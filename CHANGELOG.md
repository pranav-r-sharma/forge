## Unreleased (v0.15.0-work)

User-visible changes since 0.14.0 (package version not yet bumped).

**Fixes and behavior**
- Context meter now counts the whole prompt (cached part included); before, it read about 2% when the prompt cache was warm.
- The agent no longer stops mid-task on an empty reply or a reply that only says what it will do next ("Now I'll write the tests:"); it is prompted to continue (up to 2 times).
- Messages sent while a chat is busy are queued (Edit / Remove / Send now) instead of refused. In Agent/Auto/Outcome the running agent sees them at its next step; the rest run after the turn. Stop keeps the queue.
- `search_code` is now a grep: `regex`, `caseSensitive`, `wholeWord`, `context`, `include`/`exclude`, `path`, `mode` (lines/files/count/extract), `multiline`, `maxResults`; uses VS Code's bundled ripgrep with a built-in fallback.
- New file-mailbox bridge so a Cursor agent can hand tasks to Forge (`forge.bridge.enabled`, default off; `forge.bridge.defaultMode`). See `docs/CURSOR_BRIDGE.md`.
- Large file writes no longer truncate: the output cap is derived from the context window, `write_file` accepts `append: true`, and the model is nudged not to resend a whole file.
- A zero output cap no longer drops MLX to its 512-token default; Forge compacts once, then stops the turn if the prompt still fills the window.
- Tool-argument fixes: `read_file` `line_start`/`line_end`, nested tool calls are unwrapped, `run_command` accepts an argv array.
- Verify-before-done: after a turn that edited files, Forge runs a check before accepting the final answer (auto-detects `check.sh`, `npm test`, `pytest`, and similar).
- All your follow-up messages are pinned word for word through context compaction.
- Settings panel shows a machine profile and recommended settings, with Apply.
- Prompt-prefix stability: volatile context moved out of the system prompt. On MLX (gpt-oss-20b) append-only steps hit about 97% cache and prefill about 15x faster.
- Loop detector works in any agent mode and only exempts reads of new ranges.
- Changing MLX settings (including context) restarts the managed server, or waits until the current turn ends.
- Optional requirements checklist (off by default; it costs extra nudges and time in the A/B).
- Removed `forge.requirements.llmExtract` (it was never implemented).

**New settings (default)**
- `forge.maxOutputTokensCeiling` (0 = no ceiling; only used when `forge.maxOutputTokens` is 0)
- `forge.singleMessageSharePct` (25)
- `forge.verifyBeforeDone` (`auto`; `off` | `auto` | `custom`), `forge.verifyCommand` (empty), `forge.verifyTimeoutSec` (300)
- `forge.requirements.enabled` (false), `forge.requirements.maxNudges` (2), `forge.requirements.showInPrompt` (true)
- `forge.context.pinnedUserMaxChars` (40000)
- `forge.mlx.prefillStepSize` (0), `forge.mlx.promptCacheSize` (0), `forge.mlx.decodeConcurrency` (0), `forge.mlx.promptConcurrency` (0), `forge.mlx.draftModel` (empty), `forge.mlx.numDraftTokens` (0); 0 means the server's default
- `forge.ollama.numBatch` (0 = Ollama's default)
- `forge.mlx.modelLibraryPath` (`~/.cache/huggingface/hub`), `forge.mlx.extraModelFolders` (empty)

**Changed defaults (generous limits for large-memory Macs)**

## 0.14.0

A three-part follow-up request, explicitly framed as three separate technical questions but — per the request itself for the third — implemented with the checkpoint/task-ledger/orchestration piece "designed together rather than as three separate features": (1) whether to standardize Forge's MCP integration and how, given the tension between MCP's native tool-calling and Forge's fenced-JSON text-contract loop; (2) root-causing recurring `write_file` indentation corruption; (3) unifying checkpoint/resume, mandatory task logging, and sequential sub-agent orchestration around one mechanism instead of three. All three are in this release.

Verified with three new runtime test files (`test_v14_mcp_standardization.ts` 28 assertions — including a real spawned-subprocess MCP server fixture, not a mock, same standard as every prior MCP test — `test_v14_indent_hardening.ts` 23, `test_v14_task_manifest.ts` 38 — 89 new assertions total) plus the full existing suite (729 assertions across the prior 19 test files, all still passing — 818 total, three of which needed small updates for this round's renames rather than behavior regressions: `test_v11.ts`/`test_v12_mcp_http.ts` for the MCP field/namespacing rename, `test_v12_indent.ts` for one indentation scenario whose correct behavior genuinely changed, and `test_v12_orchestration.ts`'s fake `ChatStore` stub for the `writeTaskManifest`/`writeTaskReport` rename), a clean shim-based `tsc -p tsconfig.selfcheck.json` pass, and `node --check` on the webview JS. Not yet run inside a real VS Code extension host — same caveat as every release so far, see README → Testing.

### 1. MCP standardization

- **Native JSON Schema passthrough, both directions.** Pre-0.14.0, a connected MCP server's real `inputSchema` (fetched from `tools/list`) was silently discarded after being used once to build a generic placeholder — the model's system-prompt `exampleArgs` for an MCP tool was always just `{}`. `mcpManager.ts` now stores the schema on `DynamicToolSpec` and derives both `exampleArgs` (type-appropriate placeholders, required properties preferred, enum's first member used) and a parameter summary appended to `describe` (`query: string, limit?: number`) via new `exampleArgsFromSchema()`/`summarizeSchemaForDescribe()` — a real, if heuristic, use of the schema Forge was already fetching and throwing away.
- **Structured content-block splitting**, not raw-string flattening. `mcpClient.ts`/`mcpHttpClient.ts`'s new shared `splitMcpContentBlocks()` separates an MCP `CallToolResult`'s content blocks into `text` (fed to the model, as before) and everything else — `image`, embedded `resource`, or any other block type — as a new `ToolResultAttachment[]` on `ToolResult` (also threaded through `AgentEvent`'s `tool_result`, `webview/protocol.ts`, and rendered in the transcript: an `<img>` for images, a labeled chip otherwise). This is the concrete fix for "data to show the user" vs. "data to feed back into the loop": a chart a custom MCP returns is no longer either silently dropped or inlined as an enormous unreadable base64 blob into the model's own context — the model sees a one-line heads-up ("+1 non-text content block") and the actual image renders in the UI.
- **The text-contract vs. native-tool-calling boundary was already exactly the adapter layer described in the request** — `mcpManager.ts`'s `buildToolSpec()` already translated MCP's `tools/call` JSON-RPC into Forge's own `ToolSpec`/`ToolResult` shape, and the model-facing fenced-`forge_action` contract (`toolProtocol.ts`, `systemPrompt.ts`) never needed to know an MCP server was even involved. No changes were needed to the model-facing contract itself to confirm this — it was already separator/shape-agnostic; this release only had to fix what the adapter did with schema and content on the way through.
- **Namespacing switched from `mcp_<server>_<tool>` to `mcp__<server>__<tool>`** — the exact double-underscore convention Claude Code itself uses, so a tool name unambiguously parses back into server/tool parts even when either contains an underscore (`mcp_My_Server_echo` was already ambiguous about where the server name ended). `DynamicToolSpec` also now carries `serverName`/`remoteName` as real fields (set once in `buildToolSpec()`) rather than needing every caller to re-parse them back out of the namespaced string.
- **Error-format parity**: an MCP tool denial or failure was already close to a built-in tool's `{ok: false, content}` shape; the one real gap (the field was called `text` on `McpCallResult`, `content` everywhere else) is now closed, so `agentLoop.ts` needs zero MCP-specific branching to render either kind of failure.

**Known loopholes/judgment calls:**
- `exampleArgsFromSchema()`/`summarizeSchemaForDescribe()` are heuristic synthesizers, not a JSON Schema validator — they produce a plausible-looking example and a readable one-line parameter summary from `type`/`enum`/`required`/`description`, but do not validate the model's actual tool-call args against the schema before dispatch (a malformed call still just fails at the MCP server, same as before this release). A real validator was considered and deliberately skipped — it's a meaningfully bigger dependency/scope for a benefit (catching a bad call one round-trip earlier) the existing "MCP call fails, error comes back, model retries" loop already covers, just one step later.
- Attachments are surfaced to the user but are **not** fed back into the model's own context at all, by design — even a text summary of "there was an image here" beyond the one-line heads-up would cost real context budget on every future turn for content the model itself cannot see or reason about (local models here have no vision capability Forge assumes). If a future MCP server's image output needs to inform the model's next tool call, that's a real, separate feature (multimodal tool results) explicitly out of scope here.

### 2. `write_file` indentation hardening

- **Root cause fixed**: the exact-GCD indent-width estimator (`estimateSpaceIndentWidth()`, 0.12.0) collapses to width 1 the moment a single line's indentation doesn't evenly fit the pattern (`gcd(4, 8, 11, 12) === 1`) — and a width of 1 then makes every line in the block look "confidently" resolvable, silently producing a wrong remap instead of correctly recognizing the ambiguity. New `estimateSpaceIndentWidthRobust()` uses majority-vote confidence over a small set of candidate widths instead of GCD, so one stray line (a model drifting a space or a tab partway through a long block — the request's root-cause #3, "past ~10-15 lines") no longer corrupts the whole block's estimate.
- **Per-line graceful degradation replaces the old all-or-nothing bail.** `reindentReplacement()` used to decline the entire edit (falling back to the advisory-only warning) the moment any part of the `replace` block looked inconsistent. It now reindents every line it CAN confidently resolve and leaves only the genuinely inconsistent ones exactly as the model wrote them — `writeFileTool()`'s advisory now names the specific unresolved line number(s) ("...EXCEPT line(s) 6...") instead of a blanket "declined" message covering a block that was mostly fine. The replace block's first (anchor) line is unconditionally corrected to the file's real matched depth regardless of the rest of the block's ambiguity, since it doesn't need relative-depth arithmetic at all.
- **Confirmed language-agnostic**, per the request's "is this worse in Python vs. brace languages" question: the mechanism only ever looks at leading whitespace, with zero brace/keyword awareness in either direction — a dedicated Python-style (brace-free) test proves the exact same single-outlier-line recovery works identically to the brace-language case. There is no language-specific gap to prioritize a formatter pass around.
- **The formatter-based auto-fix pass the request raised ("run black/prettier on touched files post-edit") already has an extension point** — `.forge/hooks/after-write` (`forge/hooks.ts`, pre-existing) fires after every applied write and can run any shell command against the touched file, including a formatter. No new built-in formatter integration was added; see the loophole note below for why.

**Known loopholes/judgment calls:**
- **No built-in formatter integration was added**, even though a hook-based one is possible today. There's no telemetry from this sandbox to say whether indentation drift is more common/damaging in Python (semantically significant, so it actually breaks execution) vs. brace languages (cosmetic but still bad) to prioritize — and Forge's zero-runtime-npm-dependency policy means bundling `prettier`/`black` isn't a small addition either way. `.forge/hooks/after-write` already answers "I want this auto-fixed" for anyone who wants it, at the cost of an explicit opt-in setup step rather than it working out of the box.
- **The robust estimator's candidate widths (`2, 3, 4, 8`, plus the block's own minimum observed indent) are a fixed, hand-picked set**, not derived from the file's own indent unit — a file consistently using an unusual width (e.g. 6-space) that also happens to have an outlier line could still be misjudged. This mirrors the same "won't guess when it can't tell" philosophy as the rest of this mechanism: `undefined` (decline that specific line) is still the fallback whenever no candidate reaches the confidence bar, rather than picking the fixed set's best guess unconditionally.

### 3. Checkpoint/resume, task logging, and sequential orchestration — unified

Per the request's own framing, these three were designed and shipped as one system built on the existing 0.12.0/0.13.0 task ledger, not three separate mechanisms:

- **Single source of truth for the human-readable task report.** `ChatStore`'s per-chat `.forge/chat/<id>.tasks.md` used to be built by *appending* one Markdown section per status-change event — an independent, ever-growing log that could say something subtly different from what the in-memory ledger actually believed (it never shrank or self-corrected if a task was re-planned). `writeTaskReport()` now fully regenerates the file from the ledger's current state on every change, via a new `renderTaskManifestMarkdown()` in `agent/taskLedger.ts` — the exact same `TaskLedgerEntry[]` that already backs the in-prompt digest (`renderTaskLedgerForPrompt()`). One source of truth, rendered three ways (prompt digest, JSON manifest below, Markdown report) instead of three independently-maintained representations.
- **The literal per-task resumability manifest file the request asked for.** New `ChatStore.writeTaskManifest()` writes one small JSON file per task — `.forge/tasks/<sessionId>/<taskId>.json` — kept current on every status change: task definition, status, cost tier, parent link, last known summary, and (new) a linked checkpoint id (see below). Cleaned up automatically when the owning chat is deleted.
- **`resumeTaskId`: `spawn_subagent` can now explicitly resume an existing ledger entry** instead of always creating a new one. When the model passes the id of a task it sees marked `[~]` (in-progress) or `[!]` (failed) in the rendered ledger — ids are now shown inline for exactly the tasks worth resuming, e.g. `[~] Migrate the config loader [id: task_abc_3]` — that entry is reused in place (no duplicate/orphaned ledger entry for the same work) and the fresh sub-agent's seeded context is prefixed with that entry's last known summary. Per the request's own stated preference ("fresh-seeded is cheaper... and probably more robust"), this stays a fresh sub-agent context seeded with a compact written summary, not a replayed transcript — confirming `spawn_subagent`'s existing design (always fresh-seeded, empty message history) already matched what was asked for, with no change needed there beyond adding this optional resume path. An unrecognized/stale `resumeTaskId` degrades to ordinary new-task creation rather than failing the call. Orchestration mode's system-prompt instructions were updated to actually tell the model to use it on a detected `[~]`/`[!]` entry instead of re-describing the same task from scratch.
- **Lightweight task-to-checkpoint linkage.** `TaskLedgerEntry` gained an optional `checkpointId`, stamped by `ChatSession.onTaskLedgerChanged()` with whichever checkpoint (0.9.0/0.12.0's per-turn "restore to here" mechanism) is active for the turn currently touching that task. This tells you which checkpoint to restore to for the workspace state as of when a given task was last worked on — see the loophole note below for the explicitly scoped-down part of this.

**Known loopholes/judgment calls:**
- **`checkpointId` is a "which turn last touched this" pointer to the existing per-TURN checkpoint mechanism, not a full nested per-task checkpoint system.** A genuinely separate per-sub-agent file-snapshot system (so restoring "just this one task's changes" without affecting sibling tasks worked on in the same turn) was considered and explicitly not built this round — the existing per-turn checkpoint already covers the common "undo everything since I started this piece of work" case the field exists to support, and a real nested system is a meaningfully larger change (concurrent snapshot scoping, a restore UI that understands task-vs-turn granularity) than this request's stated hardware-constrained, sequential-only use case needs today.
- **The per-task JSON manifest has no "pointer to its own mini-transcript,"** as the request's own example described, because Forge's sub-agents are deliberately fresh-seeded rather than given a persisted transcript of their own — there is no mini-transcript file to point at. The manifest instead carries the owning `sessionId`; the parent chat's own transcript is where that task's tool-call activity actually shows up. Building actual per-sub-agent persisted transcripts was considered and rejected for the same reason the request itself gave for preferring fresh-seeding: more context/storage for a form of replay that's probably less robust than a compact written summary anyway.
- **A resumed sub-agent is told the resumed task's last summary, but is not shown the actual files that summary refers to** — it has to re-read them itself via `read_file`/`search_code` like any fresh agent would, rather than Forge trying to guess and pre-load "the files this task probably touched." This keeps the context genuinely fresh/cheap as designed, at the cost of the resumed sub-agent spending its first tool call or two re-establishing state a full transcript replay would have had for free.
- **Nothing currently prunes stale per-task manifest files if a task is deleted from the in-memory ledger some other way than the whole chat being deleted** (there is no "delete a single task" operation today, so this is currently a non-issue in practice, but it's worth naming: `writeTaskManifest()` is purely additive/overwriting, and only `ChatStore.delete()`'s whole-session cleanup ever removes files from `.forge/tasks/`).

## 0.13.0

A direct follow-up request once 0.12.0's checkpoint/resume + orchestration + MCP work landed: "estimate which tasks are cheap vs. expensive before committing to the plan, so the orchestrator can order cheap-first (fail fast, preserve partial progress) or flag 'this task list will take a long time, want to review before I start' — directly useful given interruption is apparently common enough that you're building infrastructure around it." This release is exactly that — cost-aware task planning, layered onto the existing mandatory task ledger rather than a separate mechanism.

**What's new:**
- `plan_tasks` now accepts a `costTier` (`cheap`/`moderate`/`expensive`) and optional `costNote` per task, alongside the plain-string form it already accepted (fully backward compatible). When the model omits a tier, a free, dependency-free keyword heuristic (`agent/taskCost.ts`'s `estimateCostHeuristic()`) fills one in — the ledger is never left with no cost estimate at all, the same "mandatory regardless of model discipline" guarantee `spawn_subagent`'s auto-ledger-instrumentation already established in 0.12.0.
- Every ledger entry's tier is rendered into the task-ledger prompt block (`(expensive) Refactor the auth module`), alongside a new aggregate "remaining task cost" line so the model can see the overall shape of what's left, not just each task in isolation.
- Orchestration mode's system-prompt instructions now explicitly tell the model to dispatch cheap tasks first absent a dependency reason not to — fails fast on anything structurally wrong before sinking effort into the expensive work, and preserves more finished progress if the session is interrupted partway through, which is the whole point given 0.12.0's premise that interruption is common here.
- When a plan's weighted cost (`cheap=1, moderate=3, expensive=8` per task, summed) is at or above `forge.taskLedger.expensivePlanReviewThreshold` (default 8): in a non-autonomous mode (Agent), `plan_tasks` now blocks and shows a review card — the same approval-broker mechanism `run_command` already uses, extended with a second `kind: 'plan_review'` — so nothing is added to the ledger until you approve it or the model revises the plan. In Auto/Outcome mode, which never pauses for approval by design, the plan still proceeds but posts a new, visible, non-blocking `tool_warning` transcript entry instead, so you're not blindsided by a long unattended run you didn't get a chance to see coming.
- Three new settings, all under "Task ledger & cost-aware planning" in the in-chat Settings panel: `forge.taskLedger.costAwarePlanning` (default on — the whole feature; off restores `plan_tasks`' exact pre-0.13.0 behavior), `forge.taskLedger.reviewExpensivePlans` (default on — whether an expensive plan actually blocks, vs. only ever warning), `forge.taskLedger.expensivePlanReviewThreshold` (default 8).

**Known loopholes/judgment calls:**
- **The heuristic cost estimator is a small, deliberately narrow keyword regex scan** (same category of mechanism as `gamingDetection.ts`'s verify-bypass scan or the 0.10.0 indentation advisory) — it catches obvious phrasing ("refactor", "migrate", "rewrite the entire" → expensive; "read", "typo", "rename" → cheap) and defaults to "moderate" for anything ambiguous, rather than guessing in either direction. It is not, and cannot be, a real understanding of a task's actual scope — the model's own estimate (which `plan_tasks` explicitly asks for and prefers when given) is always the better signal; the heuristic exists purely as the "never left with zero estimate" fallback.
- **"Cheap-first ordering" is a system-prompt instruction, not code-enforced sequencing.** Forge's agent loop only ever executes whatever tool the model calls next — there is no scheduler that reorders a task list on the model's behalf. This is a deliberate, minimal choice: automatically reordering tasks would need real dependency information the ledger doesn't track (only a flat `parentTaskId` link, not a full DAG — see `agent/taskLedger.ts`'s doc comment), and silently resequencing a plan the model built with an implicit ordering in mind risks breaking correctness in exchange for a heuristic benefit. The model is told why cheap-first is a good idea and is trusted to apply it when there's no dependency reason not to, the same trust level "sequential, not parallel" sub-agent dispatch already relies on in 0.12.0.
- **The review-gate threshold is a single global weighted-score number, not a smarter model of "how long will this actually take."** A plan with one `expensive` task (score 8) and a plan with eight `cheap` tasks (score 8) trip the same threshold, even though they're very different shapes of work. This was a deliberate simplification over building actual time/compute estimation (which Forge has no way to calibrate against your specific hardware/model anyway) — the setting is easy to raise or lower per how noisy it feels in practice.
- **The non-blocking warning in Auto/Outcome mode is advisory, not a safety mechanism** — same precedent as the 0.9.0 gaming-detection warning: it tells you right as the plan starts that this could take a while, but nothing stops the run. Checkpoints (0.9.0/0.12.0) remain the actual safety net if an autonomous run you'd rather not have started keeps going.

Verified with a new `test_v13_costplanning.ts` (50 assertions: the heuristic estimator, `summarizePlanCost`/`renderPlanCostLine`/`renderPlanReviewDetail`/`renderPlanCostWarning`, `TaskLedger.add()`'s auto cost-fill and JSON round-trip, `renderTaskLedgerForPrompt()`'s new cost tags/aggregate line, and — through the real `runAgentTurn`, not a mocked tool — the full `plan_tasks` review gate: below-threshold pass-through, Agent-mode blocking + approve, Agent-mode blocking + deny (verifying zero ledger side effects on denial), Auto-mode warn-but-proceed, `reviewExpensivePlans:false` still warning, and `costAwarePlanning:false` fully restoring pre-0.13.0 behavior) plus the full existing suite (691 assertions across the 15 prior test files, all still passing — 741 total), a clean shim-based `tsc -p tsconfig.selfcheck.json` pass, and `node --check` on the webview JS.

## 0.12.0

A single message with four asks, closing with an explicit "don't ask me questions, figure it out and brief me at the end of any loopholes or ambiguities and what you did about them": (1) MCP integration for the user's own custom-built MCP servers, asking whether standardization was needed on either end; (2) a fix for `write_file`'s indentation handling; (3) a detached, Claude-Code-like panel UI separate from the sidebar/file-explorer pane; and (4) three related asks tied to one stated limitation ("not enough hardware, agents get interrupted") — a mandatory framework to checkpoint progress so a new agent doesn't redo work, a mandatory per-task log, and a per-chat orchestration-mode toggle where the main agent plans, then delegates to sub-agents sequentially, tracking their reports. All four are in this release; the end-of-round ambiguities/judgment-calls brief promised above was delivered directly to the user alongside this release, not as a file in the repo.

Verified with four new runtime test files (`test_v12_indent.ts` 37 assertions, `test_v12_mcp_http.ts` 20, `test_v12_persistence.ts` 12, `test_v12_orchestration.ts` 34, `test_v12_panel.ts` 13 — 116 new assertions total) plus the full existing suite (575 assertions across the prior 14 test files, all still passing — 691 total), a clean shim-based `tsc -p tsconfig.selfcheck.json` pass, and `node --check` on the webview JS. Same real-subprocess-over-mocks standard as prior rounds where it applied (the MCP HTTP transport test spins up a real `http` server, not a mock). Not yet run inside a real VS Code extension host — same caveat as every release so far, see README → Testing.

### 1. MCP integration for custom servers

- **New HTTP ("Streamable HTTP") transport** (`mcp/mcpHttpClient.ts`, new `McpClientLike` interface shared with the existing stdio `McpClient`): a `forge.mcp.servers` entry can now be either the existing stdio shape (`{"name","command",...}`, spawned as a local child process) or a new network-reachable shape (`{"name","url","headers"?}`), speaking the MCP spec's Streamable HTTP transport over Node's built-in `fetch` — JSON-RPC 2.0 POSTed to one endpoint, a response of either `application/json` or `text/event-stream`, an `Mcp-Session-Id` response header echoed back on later requests if the server sends one. `mcpManager.ts` picks the transport per entry (exactly one of `command`/`url` must be set — both or neither is rejected with a clear per-server error, non-fatal to the others) and everything downstream (namespacing, approval-gating, dispatch through `agentLoop.ts`) is transport-agnostic.
- **What this means for standardization, concretely:** Forge's existing stdio side was already fully spec-compliant (JSON-RPC 2.0, `initialize`/`tools/list`/`tools/call`) — a custom MCP built as a local process needs no changes. A custom MCP exposed as a network service needs to speak the MCP Streamable HTTP transport specifically (a single POST endpoint, JSON-RPC 2.0 bodies, `application/json` or `text/event-stream` responses) — if it currently does plain REST or a different RPC shape, that's the one adapter needed on the user's side; nothing further is required on Forge's.

### 2. `write_file` indentation handling — actually fixed, not just flagged

- 0.10.0 shipped `detectIndentMismatch()` as an advisory-only warning; the mismatched indentation still landed on disk as typed. New `reindentReplacement()` in `fileTools.ts` does the real fix: it detects the file's actual indent unit (tab, or N spaces — width estimated via GCD of observed indents, not a guessed default), anchors on the matched location's real depth in the original file, and remaps every line of the incoming `replace` text onto that scheme while preserving its own relative nesting (a line two levels deeper than the replace block's first line stays two levels deeper after remapping). Applied on both the byte-exact match path and the whitespace-normalized fuzzy-match fallback (0.11.0).
- Declines to guess (falls back to leaving the text untouched, with the old advisory warning as a residual heads-up) when the replace text's own indentation is internally inconsistent, the match is mid-line rather than at a line start, or the file has no indentation to sniff a scheme from — corrupting an edit by guessing wrong would be worse than the original problem. Template-literal spans are detected (a cheap backtick tracker) and passed through byte-for-byte so string content is never "corrected" as if it were code indentation.

### 3. Detached panel UI, separate from the sidebar

- New `ChatViewProvider.openPanel()` opens a `vscode.WebviewPanel` ("Forge") in the main editor area via a new **Forge: Open Chat in New Panel** command and a title-bar icon on the sidebar view — a real, closeable/moveable/splittable editor tab, not another sidebar-docked panel (VS Code has no API to pop a `WebviewView` itself out of the side panel, which is why this is a second, different webview host rather than a "detach" of the existing one).
- The panel is a second live window onto the *same* session, not a second chat: it renders the identical `getHtml()`/`webview.js` bundle and reuses every shared service; `post()` now broadcasts to whichever of the sidebar view / panel are currently open. The one thing that deliberately does NOT broadcast is a host's own `ready` handshake (`sendInit()` now takes an optional single target) — otherwise opening the panel would silently re-push `init` into (and visually reset) the sidebar, and vice versa.

### 4. Checkpoint-progress framework + orchestration mode

All three of these share one root cause named directly in the request ("not enough hardware... agents get interrupted") and are designed as one system, not three separate features:

- **Incremental model-history persistence (the actual interruption-recovery fix).** Root cause: `ChatSession.send()` only assigned `this.modelHistory = result.messages` after `runAgentTurn()` fully *returned* — `uiHistory` (what you see) was already persisted after every tool call via `pushEntry()`, but `modelHistory` (what Ollama actually sees on the next turn) was not, so a mid-turn crash/host-restart resumed the *next* turn from the *previous* turn's context, even though the UI still showed everything that had happened. Fixed with a new `history_snapshot` `AgentEvent`: every mutation of the loop's model-facing transcript (every tool round-trip, nudge, and final answer, via a new internal `pushMsg()` wrapper in `agentLoop.ts`) now fires this event, and `ChatSession` applies + persists it immediately — the same "apply then persist without waiting for the turn to end" treatment `uiHistory` already had.
- **Mandatory task ledger** (new `agent/taskLedger.ts`, `StoredSession.taskLedger`). A structured `{id, description, status, summary, parentTaskId}` list, mechanically rendered into every turn's prompt (`renderTaskLedgerForPrompt()`, wired through the same `buildTurnContextPrefix()` milestones/memory/project-log already use) so a fresh or resumed agent sees "what's already done, don't redo it" without re-reading the whole transcript. Deliberately **not** gated behind the orchestration toggle below — "mandatory" means it's always active: new `plan_tasks`/`update_task` tools are available in Agent/Auto/Outcome regardless of the toggle, and every `spawn_subagent` call automatically records and resolves its own ledger entry with zero model discipline required (the model doesn't have to remember to call `update_task` for delegated work — only for anything it does inline itself).
- **Per-task log** (`ChatStore.appendTaskReport()`, new per-chat `.forge/chat/<id>.tasks.md`). Every ledger status change appends a human-readable Markdown entry — the "document of their outcome" the orchestration ask calls for, generalized to every tracked task rather than only sub-agent ones — plus a terse machine-readable entry in the existing per-chat JSONL crash-recovery log (a new `'task'` `LogEntry` kind). Three logging layers now exist for three different audiences, deliberately not merged: the JSONL log is for crash reconstruction, `.tasks.md` is for a human checking "did we already do this," and `.forge/project-log.md` (0.10.0) is the cross-chat digest.
- **Orchestration-mode toggle** (per-chat, checkbox next to the mode row, Agent/Auto/Outcome only — `ChatSession.orchestrationEnabled`, `StoredSession.orchestrationEnabled`). When on, a new system-prompt fragment instructs the model to decompose the goal with `plan_tasks`, delegate each piece to `spawn_subagent` **one at a time** (dispatch, read the report, decide, dispatch the next), and re-plan or retry based on real outcomes rather than assuming success. "Sequentially not parallelly" needed no new concurrency control: `agentLoop.ts`'s ReAct loop already only ever makes one tool call per model round-trip, so two `spawn_subagent` calls physically cannot happen at once within a turn regardless of what the model intends — the toggle only changes the model's *planning* instructions, not tool availability (which is already mandatory/always-on per the point above). A live "Tasks: 3/5" progress readout sits next to the toggle regardless of whether it's on.

### Known loopholes / ambiguities and what was done about them

See the delivery message for this release for the full brief; summarized here for the historical record:
- "Standardization needed on both ends" (ask 1) was interpreted as "what transport shape does Forge need to add" rather than a protocol-version negotiation problem — Forge's stdio side already speaks standard MCP; only a new transport option was missing for network-exposed servers.
- The task ledger (ask 4a/4b) intentionally does not un-do itself on checkpoint restore (`restoreCheckpoint()` still only reverts `uiHistory`/`modelHistory`/files) — a ledger entry is treated as a durable record of work done, not part of the reversible turn state, so restoring to an earlier point does not currently erase later-recorded ledger entries.
- Sub-agents deliberately do not themselves get the orchestrator system-prompt fragment even when their parent chat has the toggle on ("sub-agents only do the limited task" was read as sub-agents should not recursively re-orchestrate) — they can still call `plan_tasks`/`update_task` against the same shared ledger if they choose to, since the tool is mode-gated, not depth-gated.
- The detached panel (ask 3) shares session state live but each webview's own `ready` handshake is intentionally NOT broadcast to the other host, to avoid one window silently resetting the other's in-progress render — this was a judgment call favoring UI stability over the two windows being byte-identical at every instant.

### Repo-aware retrieval (always on)

1. **Structural (boundary-aware) code chunking.** `search_codebase`'s indexer previously sliced every file into fixed 120-line windows regardless of content — a chunk could start mid-function-body and end mid-signature of the next one. New `indexing/chunker.ts` (`chunkFileStructurally()`) instead scans for lines that look like the start of a top-level declaration (function/class/interface/enum/struct/impl/trait/def/fn/func, decorators/attributes kept attached to what follows) across JS/TS/Python/Go/Rust/Java/C#, and prefers to cut chunks there — never before a `minLines` floor (so a barrel file of many tiny declarations doesn't explode into a flood of tiny chunks), and force-closing at a `maxLines` ceiling if no boundary shows up in time (so one huge function/minified file still gets a bounded chunk, same as before). This is a heuristic, not a real parser (no tree-sitter dependency — see the zero-runtime-npm-dependency policy in Known limitations) — it can occasionally cut in the wrong place, but strictly never does worse than the old fixed-window behavior. **Bumps the index cache format version, so existing `.forge-index.json` caches are invalidated and every workspace re-indexes once** — see `forge.embeddingModel`'s updated guidance below for picking a code-aware embedding model while you're at it.
2. **Recency and open-tab retrieval weighting.** `WorkspaceIndex.search()` now nudges cosine-similarity rankings with two small additive boosts: a chunk in a file you currently have open (`OPEN_TAB_BOOST = 0.06`), and a chunk in a file touched (by you or the agent) in the last 30 minutes (`RECENTLY_EDITED_BOOST = 0.04`, via a new `markRecentlyTouched()` hooked into `PendingEditManager.onBeforeWrite`). Both are deliberately small relative to a typical cosine-similarity gap — they can only break a near-tie or nudge a borderline result, never let an irrelevant-but-open file outrank a genuinely on-topic one elsewhere.
3. **Lightweight import-graph traversal.** New `indexing/importGraph.ts` extracts import/require specifiers (JS/TS `import`/`require`, Python `from x import y` / `import x.y`) and resolves the relative ones (`./`, `../`) against the workspace's own indexed files — deliberately not real module resolution (no `tsconfig.paths`, no `node_modules` walking, no Python package resolution). `search()` now looks at the single top-ranked hit's resolved imports and appends up to 2 of the imported files' own best-matching chunks, clearly labeled `[Pulled in because X imports this file]` — so a question that's really answered by a helper a file imports surfaces even if the query text doesn't resemble that helper.
4. **Code-aware embedding model guidance.** `forge.embeddingModel`'s description now calls out `embeddinggemma` (622MB, a meaningfully better MTEB-Code score than the default `nomic-embed-text` for a similar footprint) and `nomic-embed-code`/`qwen3-embedding` as heavier alternatives for code-heavy repos — the default itself is unchanged (to avoid silently forcing a re-download/re-index on existing installs), this is `ollama pull` guidance in the README/setting description, surfaced again in the index-build progress message when no embedding model is found at all.

### Edit-fidelity (always on)

5. **Fuzzy, whitespace-normalized search/replace fallback.** `write_file`'s `{"search","replace"}` path previously required a byte-exact match — a real, common failure mode for local models, which are meaningfully worse than frontier models at reproducing a file's exact indentation. New `findFuzzyLineMatches()`/`applyFuzzyMatch()` in `fileTools.ts`: on zero byte-exact matches, retries with whitespace-normalized whole-line matching (trim + collapse internal whitespace runs) — if exactly one location matches, the edit is applied there with an advisory note in the tool result; if 2+ match, it's refused as ambiguous (same as the existing byte-exact ambiguity check) rather than guessing. Deliberately scoped to whole-line content only — a sub-line fragment doesn't get fuzzy-matched, since that's a different (and much less safe) kind of fuzziness than "this model retyped the right lines with the wrong indentation."
6. **Lightweight structural validation advisory.** New `detectBalanceRegression()` in `fileTools.ts`: a crude, string/comment-unaware bracket-balance count (`{}`/`()`/`[]`) across the whole file before and after an edit, flagging a bracket type that was balanced before and isn't after. Advisory only (a note appended to the tool result), deliberately conservative (only fires on a clean-before/broken-after transition, never re-flags something that was already unbalanced) to keep false positives rare — same pattern as 0.10.0's indentation-mismatch advisory, and reuses the same combined-advisory-suffix mechanism in `writeFileTool()`. Also exported and reused by best-of-N's scoring (below).

### Tool-calling-protocol reliability (opt-in)

7. **Structured/constrained output via Ollama's `format` field.** New `agent/structuredOutput.ts`: an alternative to the fenced-` ```forge_action ` text contract — when `forge.structuredOutput.enabled` is on, Forge sends a JSON Schema in the `format` request field (`STRUCTURED_RESPONSE_SCHEMA`, a flat `{response_type, final_answer?, tool?, args?}` envelope) and a matching prompt-contract section, so a model/server that honors constrained decoding can't produce malformed tool-call JSON by construction. A local model ignoring the requested format from time to time is expected, not exceptional — `agentLoop.ts`'s new `resolveModelResponse()` tries the structured parse first and falls back to the ordinary defensive fenced-block parser whenever the envelope doesn't parse, so a turn never fails just because the model drifted from the schema. Off by default: this sandbox can't verify against a real server/model whether constrained decoding helps or measurably hurts reasoning quality for the small local coder models Forge targets — that's exactly the kind of thing worth trying against your own setup.

### Inference-time accuracy (opt-in)

8. **Plan-first pass** (`forge.planFirst.enabled`, `agent/planFirst.ts`). One extra, no-tool-schema model call at the start of an Agent/Auto/Outcome turn — pure reasoning, grounded with up to 3 codebase-search snippets — producing a short plan that's prepended to that turn's context for every subsequent tool-calling iteration to see. The separate-planner/executor idea: asking a small model to "plan AND act AND stay inside a strict JSON contract" all at once asks more of it per token than two focused calls. Best-effort — any failure degrades to "no plan prefix this turn," never a failed turn.
9. **Self-critique verification pass** (`forge.selfCritique.enabled`, default minimum 40 lines via `forge.selfCritique.minLines`, `agent/selfCritique.ts`). After a non-trivial `write_file` (line-count heuristic, not a real diff), one extra tightly-scoped model call asks "does this look right" (syntax errors, unbalanced brackets, an accidentally duplicated/deleted block, an obviously inverted condition) and folds a genuine concern into that same tool result, so the SAME turn can react immediately rather than only a human noticing later. The bet: a small model is often better at judging a diff than it was at producing it — narrower question, easier to get right. A plain "OK" reply means nothing to say; best-effort, never blocks or rolls back the edit.
10. **Best-of-N sampling for large full-file rewrites** (`forge.bestOfN.enabled`, default 3 samples via `forge.bestOfN.samples`, `agent/bestOfN.ts`). Scoped specifically to the single riskiest step in the loop — a full `{"content"}` rewrite of an *existing* file at or above 40 lines (`MIN_LINES_FOR_BEST_OF_N`), where one bad generation can silently discard content a targeted `{"search","replace"}` edit would never have touched. Resamples `samples - 1` more completions from the exact same prompt, scores every write_file-same-path candidate via `detectBalanceRegression()` plus a length-ratio-to-original heuristic (rejecting outright anything targeting the wrong path/tool, or suspiciously short relative to what it's replacing), and swaps in a strictly-better-scoring candidate — never blocks or forces a retry if every resample scores worse than the original.
11. **Prompt-prefix stability fix (KV-cache reuse) — found during this round's own architecture review, not requested directly, but the clearest concrete win in the whole list for anyone running a real local Ollama/llama.cpp server.** Memory facts, the project log, and the per-turn milestone digest (0.10.0) all lived inside the system message (`messages[0]`), rebuilt every turn — and milestones grow on *every* turn unconditionally. Since llama.cpp/Ollama reuse the KV cache for however much of a new prompt is byte-identical to the previous call, and a change anywhere in `messages[0]` invalidates the cache for that message AND everything after it (i.e. the entire conversation history that follows), this was silently forcing a full prompt reprocess from scratch on every single turn — turning what should be an incremental "process just the new tail" call into the same cost as if there were no history at all. Fixed by extracting this content out of `buildSystemPrompt()` into a new `buildTurnContextPrefix()`, prepended instead to the tail of each turn's own (already-new) user message — content that's genuinely new every turn now lives at the one place in the prompt that's *supposed* to be new every turn, instead of retroactively rewriting the stable front of it. `buildSystemPrompt()` itself is now byte-identical turn over turn whenever `mode`/`rulesText`/`planContext`/MCP tools/structured-output setting haven't changed, which is the overwhelming majority of turns in a session.

### Native MCP (Model Context Protocol) client integration

12. **Forge's agent can now call your own MCP servers as tools.** New `mcp/mcpClient.ts`: a hand-written, zero-runtime-npm-dependency stdio JSON-RPC 2.0 client (newline-delimited framing, request/response correlation, per-request timeout) speaking the `initialize` → `notifications/initialized` → `tools/list`/`tools/call` handshake against protocol version `2025-06-18` — a server negotiating an older version is logged, not treated as fatal, since the spec allows that. New `mcp/mcpManager.ts` owns every server listed in the new `forge.mcp.servers` setting (`{name, command, args?, cwd?, env?}` each): spawns them (one failing to start never prevents the others), namespaces every tool as `mcp_<server>_<tool>` (collision-proof against built-ins and other servers), and exposes them to `agentLoop.ts` exactly like a built-in tool. MCP tools are approval-gated through the exact same `ApprovalBroker` channel `run_command` already uses (so existing auto-approve/require-approval settings apply, no parallel approval system), available in Agent/Auto/Outcome modes only (never Ask/Plan, same reasoning as write_file/run_command), and listed in the system prompt's tool docs alongside the built-ins. **Forge: Reload MCP Servers** re-reads the config and reconnects everything, for after editing `forge.mcp.servers` or restarting a crashed server; a new "MCP servers" section in the Settings panel shows per-server connected/tool-count status. Config (including any API token a server's `env` needs) lives in plain `settings.json`, not `vscode.SecretStorage` — an honestly-documented limitation (an MCP server's config is a whole command+args+env shape, not a single secret string SecretStorage has a natural place for), same tradeoff class as the memory/logging design already accepted elsewhere in this project.

### Documentation

13. **`FORGE_CHEAT_SHEET.md`** — a comprehensive, single-file reference covering every Forge feature from the very first release through 0.11.0: what it does, how it works under the hood (briefly), and when to reach for it, organized so it's skimmable rather than a wall of prose. ## 0.10.0

A large, 13-item backlog delivered in one round ("everything, hierarchically" — bugs first, then UX features, then the architecture overhaul), plus a separate deep-dive on the actual bottleneck behind several of those items: memory/context management as a project outlives any one chat. Two of the 13 items (embedding-based chat retention, and whether prompts themselves should be pre-embedded) were analytical questions, not build requests — answered directly rather than built: an embedding model *can* help retrieval (that's what `search_chat_history` already does), but retention/recall quality depends far more on chunking and what gets embedded than on embedding prompts themselves, and pre-embedding a prompt to retrieve context before generation is exactly RAG's job, already the shape `search_chat_history` and `search_codebase` take — so no new embedding pipeline was added standalone; instead the memory/logging architecture below reuses that existing machinery. ### Fixed

1. **Mode indicator stuck on the old mode.** Reported as "doesn't recognize that the mode has changed, keeps saying I am in ask mode when it's in agent mode or auto mode." Root cause: `ChatSession.executePlan()` (the Plan → Agent handoff after clicking "Execute plan") updated `this.mode` internally but never told the webview — only a full session sync did that, and nothing triggered one here. `ChatSession` now has a dedicated `postModeChanged()` posted from both `setMode()` and `executePlan()`, and the webview applies a new `modeChanged` message immediately regardless of which code path changed it, instead of relying on a full state sync to happen to follow.
2. **Stop button freezing the chat.** Reported as "stop functionality works but makes the chat unusable, it freezes and won't take any more messages." Two independent, compounding gaps, both closed: (a) `commandTool.ts`'s `run_command` now spawns detached in its own POSIX process group and, on cancellation *or* hitting its own configured timeout, sends SIGTERM and escalates to SIGKILL after a 2-second grace period if the process is still alive — previously a single `child.kill()` (or the built-in `spawn({timeout})` option) only ever signaled the immediate child once, so a command that traps/ignores SIGTERM (or whose real work happens in a grandchild process a shell spawned) could hang forever with the turn never returning. (b) Independently, `agentLoop.ts` now races every tool call against cancellation via a new `raceToolCallWithCancellation()` — a backstop, not a replacement for (a) — so that even a tool call that never settles for some *other* reason (a bug in a less-common tool, a hung native call) can't block the turn, and therefore `ChatSession.busy`, from ever resolving. Between the two, Stop now reliably leaves the chat immediately usable again.
3. **File-reference links not opening.** Reported as "when files are referenced in the AI model, a hyperlink type thing gets created, but the file doesn't open upon clicking." Root cause: `chatViewProvider.ts`'s `openFile` handler built the target URI with a naive `vscode.Uri.joinPath(workspaceRoot, msg.path)` instead of the same `resolveWorkspacePath()` every file tool already uses — which meant a leading `./`, a leading `/` (which `joinPath` treats as an absolute-path replacement rather than workspace-relative), or backslashes from a Windows-style path all silently produced a URI that didn't point at the real file, so `showTextDocument`'s rejection always fell through to the "could not open" warning. Now uses `resolveWorkspacePath()`, same as `read_file`/`write_file`/etc. Also fixed a related webview-side bug found while investigating: the backtick-quoted-path-in-prose renderer built its `data-path="..."` attribute from an already-`escapeHtml`'d string without separately escaping `"`, so a path containing a literal double-quote character would have truncated the attribute early.
4. **Whitespace/indentation drift on targeted writes.** Reported as "whitespace and indentation issues when doing targeted writes to existing files." `write_file`'s `{"search","replace"}` path now runs a cheap, dependency-free heuristic (`dominantIndentChar()`/`detectIndentMismatch()` in `fileTools.ts`) that compares the file's dominant indent character (tabs vs. spaces) against the replacement text's, and appends an advisory note to the tool's result if they disagree — never blocking the edit or rewriting the replacement text, since a false positive (e.g. a one-line replacement with no indentation of its own) must never stop a legitimate edit. The system prompt's action contract also now explicitly tells the model to copy indentation from the matched `search` text rather than retyping it from scratch.

### Added

5. **Progress indicators (item "what file is being edited, is the model thinking, reading, or something else").** The `status` agent event (already shown as a brief line above the composer since 0.7.0) now carries a machine-readable `activity` category alongside its text — `think`/`read`/`write`/`delete`/`run`/`search`/`diagnostics`/`memory`/`delegate`/`verify`/`web`/`other`, computed centrally in `agentLoop.ts`'s `describeToolCall()` — and the webview renders a small icon per category (💭📖✏️🗑️⚙️🔍🩺🧠🤝✅🌐) instead of one generic spinner for everything.
6. **Loop-detection on/off toggle, plus an unconditional `check_background_command` exemption.** New `forge.loopDetection.enabled` setting (default `true`, also in the Settings panel) lets you turn the loop detector off entirely for a task where genuine repetition is expected. Separately (and regardless of the toggle), polling a background command's status is now *never* counted toward loop detection at all — that repetition is the whole point of the feature, and it was previously indistinguishable from a model stuck in a real loop.
7. **Kill a running background command from the chat window.** A new header panel (gear/play icon) lists every background command tracked by `BackgroundProcessManager` — running or exited, with its exit code — across every chat tab, with a **■ Stop** button on each running one, reusing the same `kill()` the `check_background_command` tool's `{"action":"kill"}` path already calls. Previously the only way to see or stop one was to ask the agent.
8. **Independent model per chat.** `resolveModelForMode()`'s priority order (session override → per-mode routing → global default) already existed; nothing ever populated the session override. New `ChatSession.setModelOverride()`, a `setSessionModel` webview message, and a "Model for this chat" dropdown in the Settings panel's "This chat" section close that gap. The composer's model button now shows `⚙ model-name (this chat)` when a chat is pinned, so it's never ambiguous which model a given chat is actually using.
9. **Unified memory + project-log architecture** (items "better way to handle memory as things change over time," "a terrific documentation skill so every major decision/checkpoint/error/progress gets logged... and can become context for new chats," and the memory/context bottleneck discussion above):
   - **Relevance-based memory selection.** `MemoryStore.renderForPrompt()` now takes an optional `queryText` (the user's current message). When the fact list is small enough to fit under the render cap, behavior is unchanged; when it overflows, facts are now ranked by keyword-overlap relevance against `queryText` (falling back to the original recency-only cutoff with no query) instead of always dropping the oldest ones — so a fact that's actually relevant to what's being asked right now survives the cut even if it's old.
   - **Forge: Compact Memory** — a new, deterministic (no LLM call) command: every current fact appears pre-checked in a multi-select quick-pick; whatever you leave unchecked is archived (not deleted) to `.forge/memory.archive.md`, timestamped, and `.forge/memory.md` is rewritten with just what you kept.
   - **`.forge/project-log.md`** — a new workspace-wide, cross-chat, human-readable log. `ChatStore.appendProjectLog()` reuses the exact same mechanically-generated milestone summary already attached to every turn's checkpoint (0.9.0) — "unify into one system," not a fourth logging mechanism alongside the per-turn milestone, the per-session crash-recovery log, and this. `ChatStore.readProjectLogForPrompt()` injects the most recent entries (capped, same recency reasoning as memory's cap) into **every chat's** system prompt via a new `projectLogText` section — the actual fix for "a new chat starts with zero knowledge of what happened in every other chat before it." **Forge: Open Project Log** reads it directly, mirroring **Forge: Open Memory File**.

### Added

1. **Validate-before-commit.** `ChatStore.saveInternal()` now reads back and `JSON.parse()`s its own just-written `.tmp` file before renaming it over the live session file. Write-then-rename (shipped earlier) already protects against a *crash* mid-write; this protects against the rarer case where `writeFile()` returns successfully but the bytes that actually landed are truncated or garbled (a full disk, a flaky network filesystem). A failed validation aborts the save, deletes the bad `.tmp`, and leaves whichever version was already saved untouched — so a bad write degrades to "this one edit didn't save" instead of "the whole chat is now corrupt."
2. **Rolling backup (`<id>.json.bak`).** Before every save overwrites the live session file, `saveInternal()` best-effort copies the file's current contents to `<id>.json.bak` — one generation of history behind current, always a complete valid session rather than a reconstruction. Only rotates when the current file itself parses as valid JSON, specifically so that re-persisting recovered content during a recovery (see below) can never overwrite a good `.bak` with the corrupt bytes it's in the middle of recovering from — an actual bug this design caught during implementation, now pinned by `testBackupRotationDoesNotSelfCorrupt` in `test_v9.ts`.
3. **`recoverCorruptedSession()` is now a 4-tier hierarchy**, each tier only tried if the one before it has nothing usable: (1) a leftover `.tmp` (0.9.0, unchanged), (2) the new rolling `.bak`, (3) new — reconstruct a readable transcript from the append-only crash-recovery log (`.log.jsonl`, written on a different, never-at-risk code path), mapping logged events to chat bubbles where there's a natural fit (user/assistant/error) and to labeled system notes otherwise (tool calls, checkpoints, mode changes) — clearly disclaimed as lossy/best-effort, since the log itself truncates long entries, (4) the empty shell with a visible data-loss notice (0.9.0, unchanged, now extracted into `buildEmptyShell()`). Whichever tier succeeds, the recovered content is saved back immediately, same as before.
4. **Forge: Export All Chats** — a new command that bundles every saved chat (open and closed/archived) into one JSON file you choose the save location for, so a copy can live somewhere Forge doesn't control (a synced folder, a git commit). Deliberately built on `chatStore.load()` for every session rather than reading files directly, so exporting also opportunistically repairs any chat currently sitting in a corrupted state — export doubles as a bulk recovery pass.

## 0.8.1

Bug report: "the chat handling is still finicky, sometimes you can click on the chat and it just won't open, it will rename but won't open, sometimes it won't close properly - it will just keep it open if that's the only chat open in window, there may be other bugs too that I haven't discovered." Root-caused two independent, compounding concurrency bugs rather than treating each symptom as its own patch — every reported symptom (and a couple more found along the way) trace back to these. Not yet run inside a real VS Code extension host — same caveat as every release so far, see README → Testing; this one is worth a deliberate multi-tab retest given what it fixes.

### Fixed

- **Root cause #1: `.forge/chat/index.json` — every chat's title/mode/open-or-closed flag — was read, modified, and written back by `save()`, `rename()`, `setClosed()`, and `delete()` with zero synchronization between them.** `ChatSession.persist()` calls `ChatStore.save()` on nearly every agent event (every tool call, every tool result, every finalized message) and never awaits or queues it at the call site, so a busy background chat tab fires off save() calls constantly. If the user closes, renames, or reopens a *different* chat in the foreground while that's happening, both operations independently read the index, mutate their own copy, and write it back — whichever write lands last wins *in full*, silently discarding the other's change. This is exactly "closing a chat doesn't stick" (a close's `closed: true` reverted back to open by a slightly-later-landing background save that read the index before the close's write landed) and explains a renamed/reopened chat's state flickering back. Fixed by routing all four operations through a single internal FIFO queue in `ChatStore` (`src/forge/chatStore.ts`) so they always run one at a time, each reading truly-current state before writing — no lost updates, regardless of how many chats are active or how fast events are firing. Also fixed a second bug in the same area: `save()` used a single, non-unique temp filename per session id for its write-then-rename, so two overlapping `save()` calls for the *same* session (trivially possible — persist() isn't queued at the call site) could race on that shared temp file; now impossible since the same queue serializes them. `index.json`'s own write was also upgraded to the same write-then-rename pattern `save()` already used for session files, for the same crash-safety reasoning (a partial write mid-crash would have looked like "every saved chat vanished").
- **Root cause #2: the extension host processes webview messages without ever waiting for the previous one to finish**, so clicking around quickly — switching to one tab right after another, or closing right after switching — can start two `switchSession`/`closeSession`/`deleteSession`/`renameSession`/`newChat` operations concurrently. Whichever one happens to finish its own async work last (e.g. a session that needed an actual disk load, since only the most-recently-used chat is preloaded on window open) wins and silently overwrites `activeSessionId`, even if it was requested *first* — this is the direct cause of "click a chat and it just won't open" (it opened, then a slower, earlier click's leftover work finished afterward and reverted it). Fixed by routing these five operations through their own FIFO queue in `ChatViewProvider` (`src/chat/chatViewProvider.ts`), deliberately scoped to just these — `send`/`stop`/every other message stays fully concurrent so an in-flight agent turn never blocks clicking Stop or switching tabs.
- **Bonus, found while root-causing #2: `switchSession` on a session whose `.forge/chat/<id>.json` couldn't be loaded silently did nothing** — no error, no toast, nothing distinguishable from "did my click even register." Now posts an explicit error toast instead, so a genuine failure (vs. a transient UI hiccup) is visible and reportable.
- **Bonus, found while writing the regression tests: `sessionsList`/`allChatsList` pushes could themselves arrive at the webview out of order.** Both are computed by an async disk read before posting, and are triggered from many independent places (a foreground tab switch, a background tab's busy indicator) — two overlapping calls can resolve in the opposite order they were started in, letting a stale snapshot land *after* a fresher one and briefly roll the tab strip back. Fixed with a monotonic sequence number stamped on each push at the moment it's called (not when its read resolves); the webview now tracks the highest sequence number it's applied per message type and discards anything older.

Rendering into the prompt is capped (~4000 chars, keeping the *most recent* facts) so even a neglected, overgrown memory file can't itself blow the context budget it exists to protect.
- **`search_chat_history` — semantic search over every past chat.** A new `ChatMemoryIndex` mirrors the existing `@codebase`/`search_codebase` machinery (`WorkspaceIndex`): chunks `.forge/chat/*.json` transcripts, embeds them with the configured embedding model, cosine-ranks results, and falls back to keyword search automatically if no embedding model is installed. Indexing is incremental and per-session — a content-hash gate means re-indexing after a turn only re-embeds the session that actually changed, not the whole chat history, so this stays cheap even in a long-running project with many past chats. The agent is nudged (system prompt) to call this instead of asking you to repeat something that sounds like it was already discussed.
- Both new tools (`remember`, `search_chat_history`) are available in Ask mode too, not just Agent/Auto — neither has a side effect Ask mode's read-only guarantee needs to gate (`remember` only ever touches `.forge/memory.md`, not your code; the other is pure read).
- `src/util/vector.ts` — `cosineSimilarity` extracted out of `workspaceIndex.ts` so `ChatMemoryIndex` doesn't duplicate it; `workspaceIndex.ts` refactored to import it, no behavior change.

## 0.3.0

Two things landed together in this release: your local hand-edits to the *installed* extension (documented in `forgechanges20260815.md`) ported into the actual TypeScript source so they survive a rebuild, plus ten requested additions. Everything below was verified with `tsc --noEmit` and targeted runtime tests (`_devtools/runtime_test/` — `test_v3.ts` and additions to `test_edit.ts`/`test_chatstore.ts`, all passing); none of it has been run inside a real VS Code extension host (see README → Testing for why that gap still exists in this sandbox). Treat this release with the same "read the diff, run the manual QA checklist" posture as any other, more so given its size.

### Ported from your local edits (now in source, not just the installed build)

- **`num_ctx` and `keep_alive` are now sent on every Ollama call** (chat, inline edit, Tab completion) — configurable via new settings `forge.numCtx` (default `32768`, not your local `262144`; see below) and `forge.keepAliveMinutes` (default `-1`, matching what you found actually works regardless of how `Ollama.app` launches its `ollama serve` subprocess).
- **Context pruning and compaction**, redesigned rather than copied verbatim — see "Context trimming" below for why.
- **The `search_codebase`/`search_code`-over-`read_file` system prompt nudge** — ported as-is.
- **`maxAgentIterations`** raised, but not to a literal `10000000` — see "Fully autonomous mode" below for why a different number and a different mechanism.

**Why `forge.numCtx` defaults to `32768`, not your `262144`:** your number was correctly derived for your machine (Mac Studio, 128GB unified memory) and is exactly right for you — set it in Settings and it'll behave identically to your local hack. But this is a setting shipped in source now, not a value baked in for one machine, and `32768` is a safer default for anyone else (or future-you on a different machine) who hasn't done that hardware analysis. Same reasoning applies nowhere else in this list; this is the one place your exact number wasn't carried forward as the default.

### Added

1. **HW utilization metrics** — live tokens/sec in the composer footer after each response, plus currently-loaded models and their VRAM footprint (via Ollama's `/api/ps`), refreshed automatically and on click. Also `Forge: Show HW Utilization` command.
2. **Auto mode** — fully autonomous: no approval prompts for edits or commands (a small hard-coded dangerous-command denylist is the one exception, and it applies regardless of mode). On a tool failure it's instructed to diagnose and try something else rather than stop and ask. Backed by checkpoints (#3) and the loop detector (#7) as its real safety net, replacing the old "stop after 25 steps" net that a fully-autonomous mode can't rely on.
3. **Checkpoints** — every user message is a checkpoint; restoring one reverts every file touched since and truncates the chat back to that point, together, so files and transcript never drift apart. Plus an append-only crash-recovery log (`.forge/chat/<id>.log.jsonl`) so a crash or a fresh session can see the last few tool calls/decisions even if the last full snapshot is slightly stale.
4. **Context trimming without information loss** — pruning/compaction now operate on a *view* built fresh for each model call, never on the archival transcript that gets persisted. The full conversation is always still in `.forge/chat/<id>.json`; only what's sent to Ollama on a given turn is bounded. This is a deliberate redesign from how the local hack worked (see the ported-changes note above) — that version compacted the same array that got saved as permanent history, which is exactly the "don't lose my information" problem being asked about here.
5. **Folders (not just files) can be `@`-tagged**, and the mention dropdown (for both `@` files/folders and `/` skills) now supports **arrow-key navigation** (↑/↓ to move, Enter/Tab to pick), not just the mouse.
6. **Search across every chat** — 🔍 in the header, searches every saved session's transcript, not just the open tab.
7. **Loop detector** — watches every tool call's outcome; if the same action repeats 3× in a row, or 4× within the last 8 steps, the turn stops with an explanation instead of continuing to burn iterations. This is what makes the higher iteration caps (below) and Auto mode's total lack of approvals safe.
8. **Fixed: Stop button showing "Could not reach Ollama" instead of just stopping.** Root cause: cancelling the in-flight request throws a plain `AbortError`, which `OllamaClient` was unconditionally rewrapping into "Could not reach Ollama at ... Is it running?" — true for a real connectivity failure, misleading for a user-initiated Stop. Fixed in `ollama/client.ts` (chat/generate) and the same pattern in the Cmd+K inline-edit flow, which had the identical bug.
9. **Clickable file references** — a tool card's path, and any backtick-quoted path in an assistant message that looks like a file (e.g. `` `src/foo.ts` ``), opens that file on click.
10. **Fixed (mitigated): hallucinated "I created/updated that file" claims.** Final answers are now scanned for change-verb + backtick-path claims ("created `foo.ts`") with no matching `write_file` call anywhere in the conversation; if found, the agent gets up to two nudges to actually make the change or correct its claim before the answer ships. If it still ships with an unverified claim, the UI shows a visible warning on that message rather than presenting it as fact. This is a mitigation (a regex-based check), not a guarantee — see README → Known limitations.

### Also changed

- `forge.maxAgentIterations` default raised `25` → `200` (Agent/Ask/Plan); a new `forge.autoModeMaxIterations` (default `100000`) covers Auto mode. The loop detector (#7), not a low iteration count, is now the actual thrash-safety-net — see the ported-changes note above for why this isn't literally unbounded.
- `ChatStore.save()` now writes to a temp file and renames over the target instead of writing the target path directly, so a mid-write crash can't leave a corrupted, half-written session file behind.
- `ChatViewProvider`'s file-mention search now also returns folders and is shared through a new `WorkspaceEntryIndex` util instead of being duplicated between `chatViewProvider.ts` and a dead, never-called copy in `chatSession.ts` (removed).
