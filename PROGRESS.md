- **CRITICAL BUG FOUND AND FIXED — write_file double-indentation.** The suite2 rerun (multi-edit + cwd fix) showed t04 only improving 30→26 iterations and t06 REGRESSING (1/2, was 2/2). Investigation: whenever a model's "search" text omits a line's leading whitespace (extremely common — it is not changing the indent, just the code), `reindentReplacement` re-added the anchor's indent ON TOP of what was already physically in the file: `"    return x"` → search `"return x"` → replace `"return y"` produced **`"        return y"` (8 spaces) — an `IndentationError` in Python**, forcing the model into `cat -A`/`sed`/`python3 -c` debugging loops (seen live in both reruns). A second instance of the same bug hit the SECOND line of a multi-line search whose later lines already carried correct absolute indentation. **Root cause:** `matchStartsAtLineStart` only checked "does whitespace precede the match", not "is that whitespace part of `search`" — so already-present real indentation and freshly-added indentation both landed in the output. **Fix** (`src/tools/fileTools.ts`): new `anchorIndentAlreadyPresent` flag — when true, `firstRealLine` gets no prefix added, and later lines' depth is computed WITHOUT re-adding `baseDepth` (their own written indentation is used as absolute, not re-based). Applies to the single search/replace path AND the new `edits`/`all` paths (same function). This is almost certainly why the earlier t04/t06 failures cost so many steps, not thinking/terse/env. 10 new regression checks (single-line, tabs, deep nesting, multi-line, edits[], plus 3 checks proving genuinely-relative reindenting still works). `npm test`: 37/37, 1,336 checks.
