# Forge v0.15.0 — suggestions

**Goal:** make Forge a fast, thoroughly vetted coding harness for real multi-file repos on a local model (target machine: M5 Max, 128 GB).

**Symptom that started this:** the agent re-reads whole files several times instead of using grep, and the harness feels slow even on very strong hardware.

## How to read this document

Every claim is tagged with how I know it:

- **[Verified]** — I read the code and the behavior follows directly from it (file/function cited).
- **[Hypothesis]** — follows from how Ollama / LLM inference generally works, but I have **not** measured it in Forge. Part 1 (measure first) exists to confirm or kill these.
- **[Idea]** — a design suggestion, not a bug.

I did not run the extension or any model while writing this. Nothing here is benchmarked.

### 0.1 Add MLX as a first-class provider (Directive 1)

**Where Forge stands today [Verified]:** it talks only to Ollama's native API. `OllamaClient` ([client.ts](src/ollama/client.ts)) is referenced from **16 source files** (agent loop, planFirst, bestOfN, selfCritique, compaction, indexing, completion, chat session, commands…), and Ollama-specific endpoints are baked in: `/api/chat`, `/api/generate` (FIM autocomplete with `suffix`), `/api/embeddings`, `/api/tags` (model picker), `/api/ps` (VRAM/HW metrics), plus the `num_ctx`/`keep_alive`/`format` options. MLX has none of these.

**Recommended approach — talk to an OpenAI-compatible MLX server, don't embed Python.**
`mlx_lm.server` (from the `mlx-lm` package) exposes OpenAI-style `/v1/chat/completions` (streaming), `/v1/completions`, and `/v1/models`. Forge speaks HTTP to it exactly as it does to Ollama today, and **also** gets LM Studio's MLX server and any other OpenAI-compatible runtime for free. Confirm the exact endpoint set/flags of the *installed* `mlx-lm` version rather than trusting this list.

Alternatives considered:
| Option | Pros | Cons |
|---|---|---|
| **A. OpenAI-compatible client + Forge-managed `mlx_lm.server` process** (recommended) | Zero Python in the extension, one client covers MLX/LM Studio/others, easy to fake in tests | Feature set = whatever the server exposes; lifecycle management is on Forge |
| B. Persistent custom Python worker (JSON-lines over stdio) using `mlx_lm` as a library | Full control: prompt-cache handling, exact token counts, timings, constrained decoding | You now maintain a Python service; harder to test; more moving parts |
| C. Use LM Studio as the MLX host | Nice GUI, model management | Extra app dependency; less control; not scriptable in CI |
| D. Run MLX only through Ollama | Nothing to build | Ollama's runtime is llama.cpp/Metal (its MLX support is not something to rely on) — defeats the purpose |

Start with **A**; keep the interface (below) clean enough that **B** can be added later if the server can't expose something we need (e.g. reliable prefix-cache control, timing stats).

**Work items (in dependency order):**

**0.1a — Provider abstraction (no behavior change).** [Idea]
- Introduce an `LlmProvider` interface: `chatStream()`, `listModels()`, `embed()`, `complete()` (raw/FIM), `capabilities()`, `runtimeStats()`. Move the current code into an `OllamaProvider`; keep all 0.14.0 tests green.
- **Capabilities** are declared per provider/model and checked by callers instead of assuming Ollama: `{ nativeTools, structuredOutput, fim, embeddings, thinkingControl, promptCacheReuse, exactTokenUsage, contextLimit }`.
- Replace the 16 direct `OllamaClient` dependencies (`deps.ollama` etc.) with the interface. The rename is mechanical; the value is that features degrade gracefully instead of failing.
- **Per-role routing:** chat, sub-agent, compaction, planFirst/critique, autocomplete (FIM), and embeddings each resolve their own provider+model. Realistic mixed setup on a Mac: **chat on MLX, embeddings + FIM on Ollama** (or vice-versa) until MLX equivalents are proven.

**0.1b — OpenAI-compatible/MLX client.** [Idea]
- Streaming SSE parsing (Node `fetch`, still zero runtime deps), abort support, retry only on connection-level errors.
- Map settings: `temperature`, max output tokens (`max_tokens`), `stop`; drop Ollama-only knobs cleanly when provider ≠ Ollama.
- **Usage/metrics:** use the response's `usage` fields for token counts; measure **time-to-first-token and tokens/sec client-side**, since a server may not report Ollama-style durations. Feature-detect anything richer.
- **Tool calling:** send `tools` when the model's chat template supports it (this model ships a `chat_template.jinja`) and parse `tool_calls`; keep the existing text protocol as the fallback (this is §6.2 done for the provider that needs it).
- **Structured output / constrained decoding:** Ollama's `format` field has no direct equivalent. On MLX, feature-detect; otherwise auto-disable `forge.structuredOutput.enabled` and rely on the tolerant text parser.
- **Thinking models:** Qwen-family templates typically take a thinking on/off switch through chat-template kwargs. Verify for Ornith and expose it (thinking tokens dominate latency on a 9B).

**0.1c — MLX server lifecycle manager.** [Idea]
- Settings (new `forge.provider`, `forge.mlx.*`): server command / venv path, model (local snapshot path or HF id), host `127.0.0.1` **only**, port (auto-pick free), `autoStart`, max KV size / context limit, prefill step size, prompt-cache size, draft model (speculative decoding) if supported, extra args.
- Start → wait for readiness (`/v1/models`) → surface load time; **one loaded model per server process**, so a model switch = restart (say so in the UI); stop on window close/deactivate; capture stdout/stderr to a **Forge output channel**; crash → clear actionable error instead of a generic "could not reach Ollama".
- **Context limit is not `num_ctx`.** For MLX the real limit comes from the model config / server flags. Read it (Ornith's `config.json` has it) and feed **that** into compaction thresholds and the per-chat context override UI, which currently assume Ollama's `num_ctx` ([contextManager.ts:36-38](src/agent/contextManager.ts), [config.ts:125](src/util/config.ts)).
- **Model picker:** list MLX models by scanning the Hugging Face cache and/or `/v1/models`; show quantization (bits/group size) and on-disk size; warn if the model's `model_type` isn't supported by the installed `mlx-lm`.

**0.1d — Setup, diagnostics, and hardware metrics.** [Idea]
- **"Forge: Set Up MLX"** wizard: check Apple Silicon + macOS version, Python version (note: system Python here is 3.14 — confirm `mlx`/`mlx-lm` publish wheels for it, or create the venv with a supported Python), create a **project-local venv** (`_devtools/mlx-venv` or `~/.forge/mlx-venv`), install a **pinned** `mlx-lm`, verify it can load the pinned Ornith snapshot **offline**, run a 1-token smoke generation. **Never `pip install` without explicit user consent.**
- **HW metrics for MLX:** `/api/ps` (used by the composer footer and `forge.showHwStatus`) doesn't exist. Use the server process's RSS/`ps`, `memory_pressure`, and client-measured tok/s; optionally a tiny helper to read MLX's own active-memory counter. Show context used / TTFT / tok/s in the footer for both providers.
- **"Forge: Check Runtime"** command (generalizes `checkOllamaStatus`): provider reachable? model loaded? capabilities detected? cache behavior detected? estimated KV growth at the current context?

**0.1e — Autocomplete and embeddings on MLX.** [Idea]
- **FIM:** Forge's Tab autocomplete relies on Ollama's `/api/generate` + `suffix`. On MLX use `/v1/completions` with the model's raw FIM tokens (needs a FIM-capable model — Ornith-9B is a chat/agent model, likely not the right one for Tab). Default: keep completion on a small FIM model (Ollama or MLX) and don't tie it to the chat provider.
- **Embeddings:** `mlx_lm.server` is for generation; for `@codebase` keep an Ollama embedding model, or add an MLX embedding server later. Don't block Phase 0 on this.

**0.1f — Tests for the provider layer.** [Idea]
- A **fake OpenAI-compatible server** fixture (same pattern as `fixtures/fake_mcp_server.js`) covering: streaming, mid-stream abort, malformed SSE, tool_calls, usage fields, slow server, crash mid-request, server not up.
- A **real-model smoke test** against Ornith, gated by an env var (`FORGE_MLX_SMOKE=1`) so it never runs in plain CI.

**Definition of done for 0.1:** with `forge.provider = "mlx"` and the pinned Ornith snapshot, a full Agent-mode turn (search → read a range → edit → verify) completes in the real extension; Stop, model switch, server crash, and server-not-running all behave sensibly; Ollama behavior is unchanged and its existing tests still pass.

**Known constraint to design around [Verified]:** most of the harness (`fileTools`, `searchTools`, agent loop) imports `vscode`. The existing runtime tests do `import * as vscode from 'vscode'` and are launched with `NODE_PATH=…/runtime_test/node_modules` ([run_test12.sh](run_test12.sh)), but **that `node_modules` (the `vscode` stub) is not present in this checkout** — so the current test scripts cannot run here as-is. ### 0.2b Test matrix and how results scale to the M5 Max (owner decisions)

**Owner intent:** "If a model is good here, it runs very well on my M5 Max. I plan to use a bigger model of the same variety on the Max, so I'm thinking proportional results."

**Test matrix (all on this Mac, same tasks, same prompts, temperature 0):**

| Arm | Runtime | Format | Notes |
|---|---|---|---|
| 1 | Ollama | `ornith:9b` (5.6 GB, GGUF **Q4_K_M**) | Quantization confirmed via `ollama show` |
| 2 | MLX | Ornith-1.5-9B **4-bit** (4.7 GB) | pinned rev `a48173b…` |
| 3 | MLX | Ornith-1.5-9B **8-bit** (8.9 GB) | pinned rev `b4b7054…` |

Per arm, record: memory used, prefill speed (prompt tokens/sec), decode speed (tokens/sec), time-to-first-token vs prompt length, prompt-cache reuse, eval pass-rate, steps, and redundant reads. Decision output: which runtime + bit-width is the best speed/quality/memory trade-off for Forge's default, and whether the 8-bit's extra quality is worth its size.

**What transfers to the bigger model on the Max — and what does not:**

| Measurement | Transfers? | Why |
|---|---|---|
| **Wasted work removed by a harness change** (fewer redundant reads, fewer round-trips, higher cache-hit %, fewer failed edits, fewer prompt tokens processed) | **Yes, as a ratio** | Prefill cost per token is *higher* on a bigger model, so tokens saved are worth *more* there, not less |
| Ranking of harness variants (A is better than B) | **Mostly yes** | A change that helps a 9B rarely hurts a bigger sibling. The reverse is not true — see next row |
| **Harness weaknesses hidden by a strong model** | **No — the test model is the harder one** | A bigger model forgives sloppy prompts, malformed tool calls, and re-reads better than a 9B. So "works on 9B" is a good *floor* for the Max; "works on the Max" proves little about 9B. This is why 9B is the right test model |
| Absolute seconds, tokens/sec | **No** | Depends on the Max's memory bandwidth and GPU cores |
| Decode speed | **Roughly inverse to model size** | Generating a token means reading the active weights from memory, so speed ≈ memory bandwidth ÷ bytes read per token. A model 3× larger (dense) is roughly 3× slower per token on the *same* machine. A mixture-of-experts model reads only its active experts, so it breaks this rule |
| Max context that fits in memory | **No** | KV cache size depends on the bigger model's layers/heads; Ornith's hybrid attention keeps it small, but confirm the bigger sibling uses the same design |
| Quality / pass-rate | **Not proportionally** | A larger model usually passes more tasks; the gap is not a fixed multiple. Re-measure |

**So "proportional" holds for the *efficiency* results and *not* for quality or absolute speed.** Practical rules:
1. Treat every Forge improvement as a **ratio** (before/after) measured on Ornith-9B, and expect it to hold or improve on the bigger model.
2. **Do not** set thresholds from 9B seconds (e.g. timeouts, "slow task" cutoffs). Make them configurable, or derive them from a measured tokens/sec at startup.
3. **Calibration run on the Max (short, once):** run the raw-model benchmark for the bigger model, then compare with the prediction from step 2 below. If prediction and reality agree, the proportional assumption is confirmed; if not, the gap tells us what differs (bandwidth, MoE, cache behavior).
4. **Scaling probe on this Mac — DONE once, now CLOSED (do not repeat; superseded by Directive 4).** Run 2026-09-26 on Ollama 0.34.3, this Mac (M5, 32 GB), `num_ctx` 4096, temperature 0, one model at a time (memory/swap-gated), 3 runs each, median. It used other models before the Ornith-only rule. Results kept for the Max-prediction step only:

   | Model | Kind | Quant | Loaded GB | Decode tok/s | Decode × GB ≈ GB/s | Clean prefill tok/s |
   |---|---|---|---|---|---|---|
   | phi4-mini-reasoning 3.8B | dense | Q4_K_M | 3.75 | 25.6 | 96 | ~721 |
   | **ornith:9b 9.0B** | dense | Q4_K_M | 5.91 | 14.1 | 83 | ~317 |
   | phi4-reasoning 14.7B | dense | Q4_K_M | 12.09 | 7.15 | 86 | not measured cleanly |
   | devstral 23.6B | dense | Q4_K_M | 14.9 | 5.37 | 80 | not measured cleanly |
   | gpt-oss 20.9B | MoE (4 of 32 experts) | MXFP4 | 12.73 | 20.8 | (264 — not meaningful for MoE) | not measured cleanly |
   | qwen3-coder 30.5B | MoE (8 of 128 experts) | Q4_K_M | 18.86 | 31.8 | (599 — not meaningful for MoE) | not measured cleanly |

   **Takeaways:** (a) for the four **dense** models decode speed × loaded size is roughly constant (**~80–96 GB/s effective** on this Mac), i.e. decode is memory-bandwidth-bound and slows in proportion to size; (b) the **MoE** models read only their active experts, so they are far faster than their size implies; (c) prefill is compute-bound and scales differently (~inverse to parameter count). **Caveats:** Spotlight was running (decode numbers are slightly pessimistic); the first prefill pass was invalid (prompt truncated by `num_ctx`, so later runs hit Ollama's prompt cache — those figures were discarded); the corrected prefill pass was stopped by the owner after two models, so only phi4-mini and ornith:9b have clean prefill numbers. Peak memory pressure: qwen3-coder took free memory from 83% to 27% and recovered fully; swap never grew.
5. When the bigger model is chosen, run the **same eval suite** on it on the Max and add a "9B vs bigger" column to the results table, so the scaling is measured rather than assumed.
6. Prefer a bigger model from the **same family** (same chat template and tool-call format), as planned — then the prompts, tool schemas and parsers tested on Ornith carry over unchanged. If it is a different family or a mixture-of-experts, re-run the tool-calling smoke test first.

### 0.2c Ornith A/B matrix — runtime × quantization (Directive 4)

**Only Ornith-1.5-9B is used.** The variables are the runtime and the bit size; everything else is held fixed.

**The arms**

| Arm | Runtime | Weights | Size | Purpose |
|---|---|---|---|---|
| **O-Q4** | Ollama 0.34.3 | `ornith:9b`, GGUF **Q4_K_M** | 5.6 GB | Today's baseline for Forge (what runs now) |
| **M-4** | MLX (`mlx-lm`, pinned) | Ornith-1.5-9B-MLX-**4bit**, rev `a48173b…` | 4.7 GB | The MLX candidate at ~the same bit width as O-Q4 |
| **M-8** | MLX (`mlx-lm`, pinned) | Ornith-1.5-9B-MLX-**8bit**, rev `b4b7054…` | 8.9 GB | Quality reference / "is 8-bit worth its size" |
| *(O-Q8, optional)* | Ollama | an 8-bit Ornith tag, **if** the Ollama library offers one | ~9–10 GB | Would complete the square (both runtimes at both bit widths). Needs a **download → requires owner approval**; not assumed to exist |

**The comparisons (each answers one question; change one thing at a time)**

| # | Compare | Holds fixed | Varies | Answers |
|---|---|---|---|---|
| C1 | **O-Q4 vs M-4** | model, ~4-bit | **runtime** | Is MLX actually faster/lighter than Ollama for this model and Forge's workload (prefill, decode, prompt-cache reuse, memory)? |
| C2 | **M-4 vs M-8** | runtime = MLX | **bit width** | How much speed/memory does 4-bit save, and how much task quality does it cost? |
| C3 | **O-Q4 vs M-8** | model | runtime **and** bits | Only as a sanity anchor: "is the cheap arm within tolerance of the best-quality arm?" — never used to attribute a difference to one cause |
| C4 | *(optional)* O-Q4 vs O-Q8 | runtime = Ollama | bit width | Same question as C2 on the other runtime, if O-Q8 exists |

**Each arm is run through all three harness arms from 0.3** — A (through Forge), B1 (raw single shot), B2 (raw minimal tool loop) — on the same eval tasks (§8.2). So the full grid is *3 model arms × 3 harness arms × N tasks × 3 repetitions*. Run the cheap raw measurements (B1, B2) on every arm first; run the full harness eval (A) on every arm afterward.

**Controls — an A/B is only valid if these are identical across arms** (assert them in the runner; fail the run if they differ):
1. **Same rendered prompt.** Ollama and MLX apply chat templates differently (Ollama's Modelfile template vs MLX's `chat_template.jinja`). For the same messages, render both and compare the **token sequence/count**; if they differ (system-prompt placement, thinking-mode default, tool-call format), record it and neutralize it before comparing — otherwise the runtime "difference" is really a prompt difference.
2. **Same sampling.** Temperature 0 (or a fixed seed), and set `top_p`, `top_k`, repetition penalty, max output tokens **explicitly** on both — Ollama and MLX have different defaults.
3. **Same thinking mode** (on or off, stated per test) and same stop sequences.
4. **Same context size** and the same prompts, files and task repo (pinned commit).
5. **One model resident at a time on this 32 GB Mac.** Unload the Ollama model before loading the MLX server, and vice-versa — two 5–9 GB models plus KV cache plus the OS is otherwise a memory-pressure confound. Check free memory/swap before each arm; skip or abort as in the earlier probe (free < 50%, swap growth > 1 GB).
6. **Cold vs warm are separate columns.** Discard the first run (weight load / shader compile); report cold-load time separately.
7. **Repetitions:** ≥ 3 per cell, report median and spread. Background load (Spotlight, indexing) is recorded, and runs with an obvious disturbance are repeated.
8. **Record for every result:** hardware (M5, 32 GB — and later the Max), macOS, Ollama version, Python / `mlx` / `mlx-lm` versions, model revision (SHA), quantization, context size, seed, date.

**What is measured per cell**

| Group | Metrics |
|---|---|
| Speed | time-to-first-token vs prompt length; prefill tok/s; decode tok/s; total wall time; cold-load time |
| Memory | resident model memory; peak memory during a 4k / 16k / 32k prompt; free-memory low-point; swap growth |
| Prompt cache | second-request TTFT for an identical prefix (does MLX/Ollama reuse it, and does the hybrid-attention model change that?) |
| Quality | eval pass-rate; tool-call parse failures; edit-apply failures; and a cheap **greedy-agreement proxy** — run a fixed set of prompts at temperature 0 on M-4 and M-8 and record *where* their token streams first diverge (an early divergence flags larger quantization drift without needing a full eval) |
| Harness | steps, redundant reads, prompt tokens sent vs actually processed, tool time, compaction time (from the trace log, §1.1) |

**Decision rules (thresholds are set *after* measuring run-to-run noise, not before):**
- **Runtime (C1):** prefer MLX only if it is meaningfully faster **and/or** lighter *and* its eval pass-rate is not worse than O-Q4 by more than the measured noise. Otherwise keep Ollama as the default and MLX as opt-in.
- **Bit width (C2):** prefer 4-bit as the default unless 8-bit passes clearly more eval tasks / has fewer tool-call failures than noise explains. If 8-bit only wins on the greedy-agreement proxy but not on tasks, treat the difference as not mattering.
- **Report format:** one table per comparison (C1, C2, C3), each cell "median ± spread", plus a one-line verdict. Store raw results under `_devtools/bench/results/<date>-<hardware>-ornith-<arm>.json`.

**Max stage.** After the Mac-mini-scale results here, repeat the *raw* benchmark (B1) and the eval suite on the **M5 Max** for the same arms and add the columns there. ### 0.3 A/B: harness vs. calling the model directly (Directive 3)

**Purpose:** when a task is slow through the harness, find out *whether the harness or the model is the cause* — and which part of the harness.

**Trigger:** any eval task whose harness wall-time exceeds **2× the raw-model time** or takes more than K steps; plus any task the owner flags as "feels slow".

**Three arms per task** (same model, same quant, same runtime, temperature 0):
| Arm | What it is | What the difference tells us |
|---|---|---|
| **A — Harness** | The task as a user would run it (real system prompt, tools, loop, pruning/compaction) | The real experience |
| **B1 — Raw, single shot** | One model call with the relevant files/context **inlined** in a minimal prompt, no tools | Lower bound for time and an "is the model even capable" check. `A − B1` = total harness cost |
| **B2 — Raw tool loop, minimal prompt** | Same loop but a tiny prompt and the minimal tool set | Isolates **prompt/tool-doc overhead and step count** from the model itself. `A − B2` = cost of the system prompt, memory/log prefix, pruning, compaction, extra tools |

**What we record per arm:** wall time, steps, prompt tokens *sent* vs *actually processed*, output tokens, TTFT, tok/s, tool time, compaction time, files read (and repeated reads), pass/fail, and the diff produced. Then a **decomposition table**: model prefill / model decode / tool execution / harness overhead (compaction, hooks, UI events, persistence).

**Decision rule:** if B1 is fast and correct but A is slow → the harness is the problem, and the decomposition says where. If B1 is *also* slow or wrong → it's the model/runtime (try quantization, context size, thinking off, a different model) — not something to "fix" in the harness.

**Implementation prerequisite — a headless runner.** [Idea] Today the loop can only run inside VS Code (or via a `vscode` stub). Add a small CLI (`forge-bench`, in `_devtools/`) that runs the agent loop against a task directory with a `WorkspaceFs` abstraction and a stubbed approval broker, and prints a JSON result. This is more than a test convenience: it is the only way to get repeatable, scriptable A/B numbers, and it gives the project a terminal mode for free. Suggested layout:
```
_devtools/bench/
  tasks/<name>/{repo/, task.md, check.sh, meta.json}
  run.ts            # --task --arm A|B1|B2 --provider mlx|ollama --model --runs N
  results/<date>-<hardware>-<model>.json
  report.ts         # renders the decomposition table
```

### X-B. CONFLICTS — compared, with a verdict

**C1 — Wire format for tool calls**
| | Spec | Forge today / this doc |
|---|---|---|
| Approach | Always a JSON envelope `{thought, plan, actions[], message, done}`, because Copilot has no native tools | Fenced `forge_action` block (one call per turn); optional JSON envelope; native `tools` not yet used |
| Strength | One format, multi-action per turn, easy to validate | Simple for weak models; tolerant parser |
| Weakness | Model must emit a large structured object every turn (more output tokens, more ways to be malformed); `plan` re-sent every turn | One call per turn = many round-trips |

**Verdict: neither as-is — a three-tier ladder.** (1) **Native tool calling** when the model's chat template supports it (Ornith ships a template; verify) — the model is trained for exactly this format, output is shortest and most reliable, and it supports multiple calls natively. (2) **Envelope-with-`actions[]` (spec's shape, but *without* the mandatory `plan`/`thought` every turn)** as the text fallback — this gets multi-call turns. (3) The existing **fenced block** kept as the last-resort parser. The spec's design is right for *its* constraint (no native tools); Forge doesn't have that constraint on MLX.

**C2 — Format of tool results fed back**
Spec: `{"tool_results":[{id, ok, output, truncated}]}` (JSON). Forge: `[Tool "x" result]\n<plain text>`.
**Verdict: Forge's plain delimited text, plus call ids and an `ok`/`truncated` header when there are multiple parallel calls.** JSON-encoding file contents escapes every newline/quote — that inflates tokens and makes code harder for a small model to read. Ids are the only part of the spec's format that's needed (to match parallel results to calls). Under native tool calling the template handles this anyway.

**C3 — Compaction trigger: 85% vs Forge's ~50%**
Spec compacts at 85% of budget; Forge's threshold is `numCtx × 4 × 0.5` chars ([contextManager.ts:36-38](src/agent/contextManager.ts)).
**Verdict: keep Forge's lower trigger, but make it a setting and tune it on the eval suite; use the spec's *batching* idea.** For a cloud model with 128k context, 85% is fine. For a 9B local model, quality drops and prefill cost grows well before the window is full, so triggering later is *worse* here. Adopt from the spec: compact the **oldest third in one batch** (which also fits my append-only/hysteresis goal in §2.1) and the preserve-list in X9. Starting hypothesis: trigger ~60–65%, compact down to ~40%; let the eval decide.

**C4 — Undo: shadow-git repo vs Forge's lazy per-file snapshots**
| | Shadow git (`GIT_DIR`≠workspace) | Forge lazy capture ([checkpoints.ts](src/agent/checkpoints.ts)) |
|---|---|---|
| Captures shell-made changes (`sed -i`, codegen, formatters, `npm install` lockfile edits) | **Yes** | **No** — by its own design "file content only ever changes via a recorded write" is false once `run_command` runs, especially in Auto/Outcome mode |
| Cumulative `/diff` of everything changed | Free (`git diff`) | Must be computed |
| Cost per turn | A snapshot of the workspace each mutating turn (git is fast, but nonzero on huge repos) | ~Zero — only records a file when it is about to be written |
| Dependencies | needs `git` (present on macOS with Xcode CLT) and careful env isolation | none |
| Risk | Must never touch the user's real git state/hooks; binary/large files | Misses anything outside `write_file` |

**Verdict: hybrid.** Keep lazy capture as the fast default for `write_file`-only turns. **Add a shadow-git snapshot only for turns that run a command** (or always in Auto/Outcome mode). That closes the real gap (shell mutations in unattended modes) without paying snapshot cost on every turn, and gives a cumulative diff. Test that the user's real `git status` is untouched (spec §18.4).

**C5 — Understanding code: tree-sitter vs LSP vs Forge's heuristic chunker**
| | tree-sitter (spec) | VS Code LSP providers (my §3.4) | Current regex chunker |
|---|---|---|---|
| Works headless (CLI/bench) | **Yes** | No (needs the extension host) | Yes |
| Accuracy | Syntax-level (definitions/outlines); not semantic | **Semantic** (real references, rename, types) | Approximate |
| Dependencies | WASM runtime + per-language grammars (breaks *zero runtime deps*) | None (uses installed language extensions) | None |
| Availability | Always | Only if the language extension is installed and loaded | Always |

**Verdict: LSP first in the extension, tree-sitter later and optional, keep the chunker as the universal fallback.** LSP gives what tree-sitter can't (rename, real references) at zero dependency cost, which is what multi-file refactors need; the spec chose tree-sitter because a standalone CLI has no editor. Revisit tree-sitter WASM **only** for the headless CLI/bench (X20), as an opt-in dev dependency, and only if the chunker's outlines prove too weak in the eval.

**C6 — Read-before-write: hard invariant vs guarded**
Spec: an edit is refused unless the file was read this session **and** the hash still matches. My §4.3: warn if the file changed since it was read.
**Verdict: a middle path.** (a) File **changed since it was read** → refuse and show the diff (spec is right; that's the clobber bug). (b) File **never read** → allow a `search/replace` **only if** the `search` text matches exactly/uniquely (the match itself proves the model saw that text — e.g. from a `search_code` hit with context), otherwise refuse and say "read the relevant range first"; **full-file overwrite of an existing unread file is refused** (spec is right). A blanket "must have read the whole file" rule would *force* the whole-file reads this document is trying to remove.

**C7 — Persistent shell: PTY vs pipes**
Spec: PTY (`ptyprocess`/ConPTY) with sentinel tokens so `cd`, `export`, `source .venv/bin/activate`, `nvm use` persist.
**Verdict: keep the goal, change the mechanism.** A PTY in Node needs `node-pty`, a **native module** — that breaks zero-dependency and is a recurring ABI pain inside VS Code's Electron. Use a **long-lived `bash -l` (or `$SHELL`) child over pipes** with a sentinel-delimited protocol for boundaries and exit codes; that already persists cwd/env/venv/nvm. What is lost is a real TTY (interactive programs, colored output) — mostly irrelevant to an agent. Keep the spec's fallback (one-shot with tracked virtual cwd/env) and tell the user which mode is active. Process-group kill on cancel already exists in Forge. This is high-value for the Python-data repos you work in (venv activation persisting across calls).

**C8 — Sub-agent concurrency: cap 3 parallel vs Forge sequential-by-design**
**Verdict: Forge's sequential default is better for local inference.** On a cloud API, three sub-agents genuinely run in parallel. On one Mac, concurrent requests contend for the same memory bandwidth, so each is slower (and Ollama's parallel slots multiply KV memory). Expect little or no wall-clock gain. Allow **parallel only for read-only `explorer` sub-agents, and only after measuring** that the runtime (MLX server / Ollama) actually batches concurrent requests profitably. Keep depth cap 2. (Also: parallel *implementers* would collide on the shared `PendingEditManager`.)

**C9 — Iteration cap: default 50 vs Forge 200 / 100,000**
Forge defaults `maxAgentIterations = 200` and `autoModeMaxIterations = 100000` ([config.ts:113-114](src/util/config.ts)) — effectively unbounded, relying on the loop detector.
**Verdict: budget by tokens and wall-clock, not step count.** 50 steps is too few for a real multi-file task with a 9B model taking small steps; 100,000 is not a cap. Adopt the spec's **per-turn budget with an 80% warning and a resumable stop** (X14), keep an iteration cap as a backstop (e.g. 200 in all modes), keep the loop detector.

**C10 — `why` required on every mutating action**
**Verdict: adopt as soft.** Validation that hard-fails when a 9B model omits a one-line field just adds a retry round-trip. If missing, show the diff/command and "(no reason given)"; require it (retry) only for `run_command` and deletes, where the approver genuinely needs the intent.

**C11 — `read_file` default cap: 2000 lines vs Forge 200 KB**
**Verdict: use both, whichever is smaller — and derive the ceiling from the context window.** 2000 lines (~20–30k tokens) is still nearly an entire 32k-token window. Cap by `min(2000 lines, ~15% of the context window in tokens)`, with `offset`/`limit`, and answer oversize reads with an outline (§3.2) instead of an error.

**C12 — Ignore file: `.copilotignore`**
**Verdict: `.forgeignore` + `.gitignore` (+ built-ins), one shared implementation.** Same idea; already on the roadmap.

**C13 — Hooks: `hooks.json` vs one executable script per event (`.forge/hooks/<event>`)**
**Verdict: keep script files (they work today), add an optional `hooks.json`** for matchers ("only for `write_file` on `*.py`"), multiple commands per event, and the new events (X18). Precedence: `hooks.json` entries run in addition to the script file.

## 0. Executive summary

The "re-reads whole files" problem is **not one bug, it is five mechanisms that reinforce each other** [Verified]:

1. **Context pruning deletes file contents the agent is still using.** After only the last 6 tool results, older `read_file` results are replaced by a stub, so the model must re-read ([contextManager.ts:23, :51-96](src/agent/contextManager.ts)).
2. **The search tool can't replace a read.** `search_code` returns single matched lines with no surrounding context, so the model has to `read_file` to understand any hit ([searchTools.ts](src/tools/searchTools.ts)).
3. **Edit failures tell the model to re-read the whole file.** "Re-read the file and try again" ([fileTools.ts:164-167](src/tools/fileTools.ts)) — the error gives no location or nearest-match hint.
4. **`read_file` has no cheap middle ground.** It is whole-file (up to 200 KB) or a manual line range. There is no outline, no symbol read, no "unchanged since you last read it" answer ([fileTools.ts:7-47](src/tools/fileTools.ts)).
5. **The system prompt tells the model to read before editing** ([systemPrompt.ts:83](src/agent/systemPrompt.ts)), and the loop is strictly one tool call per model round-trip, so exploring N files costs N full prompt evaluations.

The "slow on 128 GB" problem is most likely **prompt re-processing (prefill), not generation speed** [Hypothesis]: the sliding prune window rewrites old messages every iteration, which should invalidate Ollama's prompt/KV cache from that point on, forcing near-full re-evaluation of the conversation on each step.

**Recommended 0.15.0 theme: "Read less, search better, re-process less, prove it."** — and everything in **Phase 0 above (MLX provider, Ornith-9B verification, harness-vs-raw A/B) goes first.**

### 1.1 Per-iteration trace log — [Idea], small effort

Write one JSON line per agent iteration to `.forge/traces/<sessionId>.jsonl`:

```
{ iter, tool, args (hashed/truncated), resultChars, promptTokensSent, promptEvalCount,

  totalMs, prunedMessagesCount, compactionFired }
```

What it answers:
- **Is the KV cache being reused?** If `promptEvalCount` ≈ full prompt size every iteration, prefix reuse is broken (§2.1).
- **How many times is the same file read?** Group by `(tool=read_file, path)`.

### 1.4 Accurate hardware readout: RAM, free memory, GPU, context — P0 (owner requirement, added 2026-09-26)

**Owner requirement:** "I want clear and accurate measures of hardware usage in the harness. It already shows RAM and context but sometimes not accurately. Make it so — I want to know **free memory** as well, and **GPU usage** as well." It must be **correct first**: a missing number is acceptable, a wrong number is not.

**What is wrong today [Verified in [hwMetrics.ts](src/util/hwMetrics.ts) and measured on this Mac]**

| Problem | Evidence |
|---|---|
| **RAM "used" is overstated.** `getRamStatus()` computes `used = os.totalmem() − os.freemem()` ([hwMetrics.ts:6-14](src/util/hwMetrics.ts)). On macOS `freemem()` counts only *never-touched* pages, not memory the OS can reclaim instantly (inactive/cached files) | Measured now: Node `freemem` = **7.7 GB** → harness shows **24.3 GB used** of 32. `memory_pressure` / `kern.memorystatus_level` says **61% free**; `vm_stat` shows ~13.5 GB free+inactive+speculative. True in-use ≈ 12–13 GB — the display is off by roughly **2×** |
| **No GPU reading on a Mac.** `getGpuStatus()` only runs `nvidia-smi` ([hwMetrics.ts:78-124](src/util/hwMetrics.ts)); its own comment says it returns nothing on Apple silicon | The GPU readout is simply absent for your setup |
| **"VRAM" means something different on Apple silicon.** Memory is *unified* — there is no separate VRAM pool. Ollama's "VRAM" figure is the model's size in the same RAM | A "VRAM used / VRAM total" bar is misleading; the real limit is the OS's GPU working-set cap (`iogpu.wired_limit_mb`, `0` = system default, roughly two-thirds to three-quarters of RAM — confirm on the machine) |
| **Context "used" is estimated in characters** (÷4) rather than measured | See §2.1b — Ornith measures ~2.5 chars/token on code, so the context meter can under-report real usage |
| **`estimateSuggestedNumCtx()` is a guess** ([hwMetrics.ts:42-56](src/util/hwMetrics.ts)) scaling context by idle RAM | Replaced by a *measured* per-token cost below |

**What to show (four groups, every value labelled with its source and age)**

| Group | Values | How to get them on macOS — no sudo, no new dependencies |
|---|---|---|
| **Memory** | Total; **Used**; **Free/available**; **memory pressure %** (the number macOS itself uses); **swap used**; compressed | `sysctl hw.memsize`; `sysctl kern.memorystatus_level` (= free %, cheap and exact); `vm_stat` → **read the page size from its header — it is 16,384 bytes on Apple silicon, not 4,096** (hard-coding 4096 would make free memory read ~4× too small); `sysctl vm.swapusage`. Define: *Available = free + inactive + speculative + purgeable*; *Used = Total − Available*. Show pressure % as the headline (it accounts for compression); show GB as detail |
| **Model / server process** | Resident size of the model runtime; how much is weights vs context cache | Ollama: `/api/ps` `size` (and `context_length`). MLX server: process footprint (`ps -o rss=`, or `footprint <pid>`). Predicted context-cache cost from the measured slope below |
| **GPU** | **GPU utilization %**; GPU memory in use vs the GPU working-set limit | `ioreg -r -d 1 -w0 -c IOAccelerator` → `PerformanceStatistics` → **`Device Utilization %`** (also Renderer/Tiler %), **`In use system memory`**, **`Alloc system memory`** — verified available here without sudo (read 23% / 8.9 GB during a model run). **`powermetrics` (GPU power/frequency) needs sudo → removed from the product entirely** (Directive 6); it may be used by the developer, by hand, only to cross-check the `ioreg` numbers during development |
| **Context & speed** | Context used / limit in **real tokens**; prompt tokens *processed* vs *cached*; TTFT; prefill and decode tok/s; server-truncation warning | Server-reported `prompt_eval_count` and durations; the truncation check in §2.1b |

**Design rules**
1. **One sampler in the extension host**, not one per webview. About 1 Hz while a turn is running, ~0.2 Hz idle. Each command has a timeout and runs off the UI thread; results are cached so the UI never blocks.
2. **Accuracy over completeness:** if a source fails, show `n/a` (and why in a tooltip) — never fall back to a plausible-looking wrong number.
3. **GPU utilization is a sampled instant, and it jumps.** Show a short moving average (a few seconds) plus the peak during the current turn.
4. **Units:** GB = 2³⁰ bytes, stated once in a tooltip; same unit everywhere.
5. **Every number has a tooltip** with its definition and source (e.g. "Used = total − (free + inactive + speculative + purgeable), from `vm_stat`").
6. **Same values feed the trace log (§1.1)** per iteration: memory low-point, swap change, average and peak GPU %, so every benchmark automatically records the hardware state it ran under.
7. **Works for both runtimes.** The hardware readout is system-level, so it is identical for Ollama and MLX; only the "model/server process" group differs.

**Memory guard — "push it, but don't crash it" (built on the same sampler)**
- Refuse (or ask before) raising the context beyond what is predicted to fit: `predicted = weights + per_token_cache_cost × tokens`, capped below the GPU working-set limit and a free-memory floor.
- Warn, then pause, when memory pressure is high (e.g. free < 20%) or swap is growing while a model is loaded; never start a load that is predicted to exceed the cap. (The same gates were used successfully in the probes: free-memory floor, swap-growth limit, predicted-size check.)
- **Measured input for Ornith-1.5-9B (Ollama, Q4_K_M), this Mac:** memory at load = ~5.9 GB weights + **~35 KB per token of context** (6.16 GB at 8k → 15.09 GB at the model's full 262k, no swap growth, free memory bottomed at 41%). The context cache is small because only 1 layer in 4 uses full attention. The MLX 4-bit / 8-bit arms need their own measurement — do not assume the same slope.

**Accuracy tests (part of §8)**
- Unit tests over **recorded fixtures** of `vm_stat`, `sysctl` and `ioreg` output — including a 16 KB-page fixture and a malformed/missing-field one — asserting the parsed numbers and that `used + available ≈ total`.
- A cross-check test against `memory_pressure` (agree within a few percent).
- A manual side-by-side against Activity Monitor once, recorded in the doc.
- A test that a failing source yields `n/a`, not a number.
- A synthetic-load check (allocate and free a known amount) that the displayed change matches — done cautiously, never near the memory gates.

## 2. Performance: reduce re-processing and per-step cost

### 2.1 Make the prompt append-only so the KV cache survives — P0

**[Verified]** Each iteration, `buildPromptView()` ([agentLoop.ts:430-435](src/agent/agentLoop.ts)) runs `pruneStaleReadsView()` then `maybeCompact()` then `hardCapOversizedMessages()` over the **whole** history. `pruneStaleReadsView` rewrites any `read_file` result outside the last 6 tool results — so every iteration, one more old message flips from full content to a stub.

**[Hypothesis]** Ollama/llama.cpp reuse the KV cache only for the longest byte-identical prefix of the previous prompt. Changing message *k* invalidates everything from *k* onward. Because the pruned message is old, that is most of the conversation — so each step re-evaluates nearly the whole prompt. (The codebase already understands this principle: see the prefix-stability comment in [systemPrompt.ts:13-31](src/agent/systemPrompt.ts) — but the pruning pass undoes it.)

**Suggestion:**
- Keep the sent prompt **append-only** between compactions. Never rewrite an old message on each step.
- Prune/compact in **batches with hysteresis**: do nothing until the prompt crosses e.g. 75% of budget, then in one pass drop down to e.g. 45%, and then stay append-only again. One cache miss per batch instead of one per step.
- When pruning does happen, prefer **dropping whole old tool-result messages** (deterministic, stable) over rewriting them.
- Verify with the trace log: `cachedPromptTokens / promptTokensSent` should be high (>90%) on ordinary steps.

### 2.1b Never let the server silently truncate the prompt — P0 (found during the Ornith context probe)

**[Verified by experiment]** When a prompt exceeds `num_ctx`, Ollama does **not** error — it silently cuts it. In the scaling probe an over-long prompt was reported as exactly 2,050 tokens on three different models (i.e. cut to about half the 4,096 window). For a chat, that means the **oldest** content — potentially the original user request — can vanish with no warning.

**[Verified in code, not yet tested]** Forge's compaction trigger estimates tokens as **4 characters per token** ([contextManager.ts:36-38](src/agent/contextManager.ts)). Measured on Ornith with code-like text it is closer to **~2.5 characters per token**, so the real prompt can be ~60% larger in tokens than Forge thinks. Effect: compaction fires later than intended (roughly at 80% of the window instead of 50%), and a single large tool result can push past the window before compaction runs. The last two messages are also exempt from the hard cap ([contextManager.ts:179-191](src/agent/contextManager.ts)), and `maxContextFileKB` defaults to 200 KB (~50–80k tokens) against a 32k window.

**Suggestion:**
- Count **real tokens**: use the previous response's `prompt_eval_count` (already returned by the server) or the runtime's tokenizer endpoint, and keep a per-model measured chars-per-token ratio, instead of a fixed 4.
- **Detect truncation:** if the server-reported prompt tokens are less than what was sent, warn visibly ("the model only saw the last N tokens") and trigger compaction immediately.
- Budget explicitly: `window − reserved output − largest expected tool result`, and split/limit tool results to fit *before* they are added.
- **Pin** the original user request and the task ledger so they are never the part that gets cut (§X9).
- On MLX the behavior at the limit differs (it depends on the server's max KV size / rotating cache — **verify on the installed `mlx-lm`, do not assume**). Add a test that overfills the context on each runtime and asserts what happens.
- Note: even inside the window, a 9B model uses long context less reliably than a short one ("lost in the middle"). The usable context is smaller than the maximum; measure it with a needle-in-a-haystack check at several depths (Ornith only).

### 2.1c KV / prompt cache: hot, warm (disk), cold — P0 to measure (owner idea, 2026-09-26)

**Owner idea:** "Can't we use a KV cache, or hot cache and cold cache, to improve this? I don't even mind writing the vectors on disk and re-reading them as needed."

**Why it matters — measured cost of *not* caching (Ornith Q4_K_M, Ollama, this Mac; time to read the prompt, cold):**

| Prompt tokens | 6.6k | 13k | 26k | 52k |
|---|---|---|---|---|
| Time to read it | 29 s | 62 s | 143 s | **449 s (7.5 min)** |
| Prefill speed | 231 tok/s | 212 | 183 | 116 |

Prefill slows as the prompt grows, so long prompts are disproportionately expensive. Every *new session* or *restart* that has to re-read a long prompt pays this.

**What a KV cache is (and is not).** While the model reads a prompt it produces, for every token and every attention layer, *key* and *value* tensors. Saving them means the same tokens never need to be re-read. This is different from the **embedding vectors** used for `@codebase` search — a separate index that already exists; the two can coexist.

**Three tiers**
| Tier | Where | Cost to reuse | Use |
|---|---|---|---|
| **Hot** | In the runtime's memory | ~0 | Consecutive steps of one running turn (each step = previous prompt + a little new text) |
| **Warm** | On disk (`.forge/cache/`, **gitignored**) | Read the file back — an SSD does several GB/s (**measure here**; `dd` on a fresh file, no sudo) | New session, app restart, model unloaded, "resume yesterday's chat" |
| **Cold** | Nowhere — recompute | The table above | Only when the prefix changed |

**Size estimate (to be measured — Ollama's context allocation was ~35 KB/token; MLX may differ):** ~0.3 GB at 8k tokens, ~1.2 GB at 32k, ~1.8 GB at 52k, ~4.5 GB at 128k, ~9 GB at the full 262k. Compare with 449 s of recompute for 52k: a few seconds of disk read instead of minutes. KV quantization (8-bit / 4-bit) can shrink both memory and disk — quality effect must be tested.

**What to cache (in order of value)**
1. **Hot, within a turn — free if the prompt is append-only (§2.1).** Ollama already reuses the in-memory prefix (the probe hit it by accident at ~67,000 tok/s). Forge's current pruning rewrites old messages every step and defeats it. So the biggest win may need **no new machinery** — just stop rewriting the prefix.
2. **Warm, a "pre-warmed" project prefix:** system prompt + tool docs + rules + memory + repo map, computed once, saved, and loaded at session start. Every new chat starts with the first token in seconds, not after re-reading that prefix.
3. **Warm, per-session snapshots:** save the state after each turn (or every N tokens) so **resuming a session** — which Forge already supports — does not re-read tens of thousands of tokens. This fits Forge's existing checkpoint/resume design.
4. **Not recommended: per-file caches reused at arbitrary positions.** A token's cached state depends on everything before it, so a file's cache can't be dropped into a different position exactly. Approximate schemes exist in research; they trade correctness for speed — avoid.

**Hard constraints (the "gotchas")**
- **Exact-prefix rule:** a cache is valid only for a *byte-identical* token prefix. Changing any earlier token invalidates everything after it. So the prompt layout must be ordered **stable → volatile**: system + tools + rules first, then repo map, then conversation, with memory/log/ledger at the tail (already the case for memory). Never edit history in place; compact only in batches and accept one miss (§2.1).
- **Hybrid model caveat (Ornith is hybrid — 3 of every 4 layers use linear attention):** full-attention layers keep a per-token KV that can be cut back to any earlier position; the **linear-attention layers keep a running state that cannot be "un-read"** to an earlier position. So a saved state is valid only **at the exact position it was saved**. Consequence: save **snapshots at deliberate boundaries** (after the static prefix; after each turn), not "cut back anywhere". *Hypothesis from the architecture — verify against the installed `mlx-lm`'s cache classes before designing around it.*
- **The cache is bound to the exact model:** weights revision, quantization, KV-quantization setting, tokenizer and chat template. Key the file by a hash of all of these plus the token IDs; refuse to load on mismatch.
- **Runtime support differs:**
  - **MLX:** `mlx-lm` provides prompt-cache save/load helpers and a cache-prompt command, and its server keeps a prompt cache between requests. *Names/behavior to confirm on the installed version — do not assume.* MLX is the natural home for this, which fits the MLX-first direction.
  - **Ollama:** keeps the last prompt's cache in memory only; I know of no way to save it to disk through its API. Warm-tier persistence is an **MLX-only** feature unless that changes.
- **Privacy:** cache files contain a mathematical encoding of your repo's content. Keep them under a gitignored `.forge/cache/`, never commit or share them, and offer a "clear cache" command. Set a disk budget with least-recently-used eviction.
- **Correctness test is mandatory:** with the cache vs without it, greedy (temperature 0) output must be **identical**. If not, the cache path is broken.

**Other prefill levers (smaller, for completeness)**
- Reading *less* is still the cheapest fix (§3): every token not sent is a token not read.
- Prefill chunk size / step size (MLX server setting) can change throughput — measure.
- Speculative decoding (e.g. Splash, parked) speeds **decode**, not prefill — it does not help here.

**Experiments (Ornith only; MLX ones need the venv approval)**
1. In-session reuse: send a 50k-token prompt, then the same prefix plus a short new tail — time-to-first-token both times, on Ollama and on MLX.
2. MLX: save the prompt cache at 8k / 32k / 52k tokens — file size, save time, load time, and the **identical-output** check.
3. Hybrid behavior: try to reuse a cache after truncating the prompt at an earlier position; record whether the linear layers make it invalid.
4. KV quantization: cache size and needle-in-a-haystack accuracy at 4-bit / 8-bit vs full.
5. Disk speed: sequential read of a multi-GB fresh file (no sudo, no cache purge needed if the file is freshly written and larger than free memory — otherwise report as "cached read" honestly).
6. Add a **cache-state dimension** to the A/B matrix (§0.2c): cold, hot (in-memory), warm (restored from disk).

**Expected impact if it works:** the cold-start cost (minutes at 50k tokens) becomes a one-time event per project; each agent step then reads only its *new* tokens (seconds). That is likely a larger win than any decode-speed improvement, and it makes long-context sessions on your Max practical.

### 2.2 Replace LLM compaction with deterministic "observation masking" first — P1

**[Verified]** `maybeCompact()` calls the **main model** synchronously to summarize old messages ([contextManager.ts:110-159](src/agent/contextManager.ts)). That blocks the turn, evaluates a big transcript, and changes the prefix.

**[Idea]**
- Tier 1 (free, instant): mask old tool *results* with a one-line stub that keeps the useful part (`read_file src/a.ts:1-200 → 200 lines, exports foo, bar`), keep the model's own reasoning/actions.
- Tier 2 (only if still over budget): LLM summary, using a **small/fast model** (there is already a `forge.subAgentModel` concept) rather than the main model, and run it at the batch boundary from §2.1.
- Keep the existing guarantee that the persisted transcript is never touched.

### 2.3 Slim the system prompt and tool docs — P1

**[Verified]** The system prompt inlines every tool's full `describe` text ([systemPrompt.ts:59-63](src/agent/systemPrompt.ts)). `plan_tasks` and `spawn_subagent` descriptions are each several hundred tokens ([tools/index.ts:78-96](src/tools/index.ts)). This is re-sent (and, on a cache miss, re-evaluated) constantly, and long instruction blocks dilute a local model's attention.

**[Idea]**
- Short one-line `describe` for every tool; move the long guidance (cost tiers, resume semantics) into a lazily-fetched `tool_help` or just into the tool's error/first-use response.
- Only advertise tools that are useful in the current state (e.g. hide `check_background_command` until a background command exists; hide task-ledger tools unless orchestration is on).
- Measure system-prompt token count in the trace log and set a budget (e.g. ≤ 1.5k tokens).

### 2.4 Bound output and thinking tokens — P1

**[Verified]** `chat()` only sets `num_predict` when a caller passes `maxTokens`; the agent loop doesn't ([agentLoop.ts:454-464](src/agent/agentLoop.ts)). A model that starts rambling or writes a whole file inside a tool call is unbounded.

**[Idea]**
- Set a sane per-step `num_predict` (e.g. 4–8k) with a specific "continue" path if truncated mid-tool-call.
- For "thinking" models, expose Ollama's `think` control per mode (off for cheap exploration steps, on for planning) — thinking tokens can dominate latency. Check that the installed Ollama version supports this for your model.
- Add `stop` sequences for the fenced action block terminator to avoid the model generating past its tool call.

### 2.5 Ollama server tuning and runtime choice (Apple Silicon) — Ollama part P2; MLX part moved to Phase 0

**[Hypothesis]** — none of this is in Forge today, and results depend on your Ollama version and model. Benchmark each against the baseline (§1.3) before adopting.

- **Server env vars** (set where Ollama runs): flash attention (`OLLAMA_FLASH_ATTENTION=1`), quantized KV cache (`OLLAMA_KV_CACHE_TYPE=q8_0`) to cut KV memory ~half at large `num_ctx`, `OLLAMA_NUM_PARALLEL=1` (Ollama allocates KV per parallel slot, so parallelism silently multiplies memory), `OLLAMA_MAX_LOADED_MODELS` high enough that chat + embedding + completion models don't evict each other. ### 2.7 UI/streaming overhead — P2, check first

## 3. Tools: read less, find more (multi-file repos)

### 3.1 Replace `search_code` with a real, ripgrep-class search — P0

**[Verified] problems in the current implementation** ([searchTools.ts](src/tools/searchTools.ts)):
- Enumerates up to `MAX_FILES_SCANNED = 3000` files, then reads **each one serially** through `vscode.workspace.fs.readFile`, testing a JS regex. Slow on big repos; **silently ignores everything past 3000 files** (and files >512 KB).
- A matching line is a **single line**, trimmed to 200 chars — no context. The model can't understand a hit without a `read_file`, which is exactly the behavior you're seeing.
- 60-match cap is global, not per-file, so one noisy file starves the rest.
- Builds a new `RegExp` for every line of every matching file.
- Excludes are hard-coded, not `.gitignore`-aware.
- Reads from **disk**, while `read_file` reads the **pending-edit overlay** (`ctx.readEffective`). So after the agent stages an edit, `search_code` cannot see it but `read_file` can — inconsistent and confusing.

**Suggestion:** back it with VS Code's own ripgrep (`vscode.workspace.findTextInFiles`, zero new dependency) or spawn `rg` when present. New parameters:

| Param | Purpose |
|---|---|
| `context` / `before` / `after` | Show N lines around each hit — usually removes the need to read |
| `output: "files" \| "lines" \| "count"` | "Which files mention X?" without any content |
| `glob`, `type` (e.g. `ts`, `py`) | Scope by path/language |
| `case_sensitive`, `whole_word`, `multiline`, `fixed_string` | Explicit, instead of inferring from `/…/` syntax |
| `max_per_file`, `max_results`, `offset` | Fair distribution and paging, with a "N more" footer |
| `path` | Search inside one directory |

Then overlay the pending-edit contents so results match what `read_file` sees. Return a compact, grouped format (`path` header once, then `  42: line`) to save tokens.

### 3.2 `read_file`: dedupe, outline, symbol, and multi-range — P0

**[Verified] problems** ([fileTools.ts:7-47](src/tools/fileTools.ts)):
- Whole file up to `maxContextFileKB` (default **200 KB ≈ ~50k tokens**), but the default `numCtx` is 32,768 tokens (~130k chars) ([config.ts:121-125](src/util/config.ts)). A 150–200 KB file is *allowed* in a single result that is larger than the entire window; the last two messages are exempt from `hardCapOversizedMessages()`, so it goes in whole. Derive the size guard from `numCtx` (e.g. a single result ≤ ~15% of the window), not from a fixed KB.
- Every line gets a `NNN| ` gutter — extra tokens on every read.
- No way to ask for structure without content.

**Suggestion:**
1. **Read ledger.** Track `path → {contentHash, ranges already returned, step}` for the turn. On a repeat read of an unchanged file/range return: `Unchanged since you read it at step 4 (lines 1-200). Not resending. Ask for a specific range or use search_code.` Cheap, and it directly attacks the symptom. (Also re-serve the actual content if the earlier result was pruned — see §2.1 — so this and pruning must cooperate.)
2. **`mode: "outline"`.** Return imports, top-level symbols with line ranges, and signatures (LSP document symbols — §3.4 — or the existing structural chunker in [indexing/chunker.ts](src/indexing/chunker.ts) as a fallback). A 2,000-line file becomes ~40 lines; the model then reads exactly the range it needs.
3. **`symbol: "loadConfig"`.** Read just that symbol's body (+ a few lines of context).
4. **`ranges: [[10,60],[200,240]]`.** Multiple ranges in one call.
5. **Default large files to outline + first N lines** instead of returning an error that costs a whole round-trip ("Re-run read_file with start_line/end_line…").
6. **`read_files`** (batch) — see §6.1.
7. Make the line-number gutter compact (or optional), and make sure it stays consistent with what `write_file` matching expects (it does not match on gutters today).

### 3.3 Add the missing navigation tools — P1

**[Verified]** The only ways to locate things today are `list_dir` (depth ≤ 4, 400 entries) and content search. There is no find-by-name tool.

- **`find_files`** — glob/name search (`**/*auth*.ts`), `.gitignore`-aware, sorted by recency/relevance.
- **`list_dir`** fixes: [paths.ts `isIgnoredDir`](src/util/paths.ts) hides **every** directory starting with `.` — including `.github/`, `.vscode/`, `.devcontainer/`, which matter in real repos. Switch to `.gitignore` + an explicit ignore list, and show file sizes/line counts so the model can decide whether a file is worth reading.
- **Git read tools** — `git_status`, `git_diff` (staged/unstaged/against a ref), `git_log`, `git_blame` (range). Today these all require `run_command` (an approval prompt each time in Agent mode). "What did I change?" is the most common multi-file question.

### 3.4 Use the language server for precise multi-file work — P1 (highest leverage for multi-file repos)

**[Idea]** VS Code already has, for any language with an extension installed, the exact machinery a coding agent needs, exposed as commands (`vscode.commands.executeCommand('vscode.executeXxxProvider', …)`):

| Tool | Backing provider | What it replaces |
|---|---|---|
| `find_symbol(name)` | workspace symbol provider | grep for `function foo` |
| `outline(path)` | document symbol provider | reading a file to see its shape |
| `go_to_definition(path, line, col)` | definition provider | reading files to chase an import |
| `find_references(path, line, col)` | reference provider | grep for a name (which also hits comments/strings) |
| `rename_symbol(path, line, col, newName)` | rename provider → workspace edit | dozens of hand-written edits, and the classic source of half-finished renames |
| `get_problems` (exists) | diagnostics | — make it automatic, see §4.4 |

Caveats to design for: results depend on the user having the language extension installed and finished loading; every tool needs a graceful "no provider, fall back to search" path; rename edits must go through `PendingEditManager` so they are staged/checkpointed like any other edit.

### 3.5 Repo map for orientation — P2

**[Idea]** An Aider-style compact map — per file: path + top-level symbol names, ranked by import-graph centrality and recent edits — injected into the turn context (with a strict token budget, e.g. 1–2k) so the model starts oriented instead of spending its first several steps exploring. The pieces largely exist already (chunker, import graph in [indexing/importGraph.ts](src/indexing/importGraph.ts), recency map). Keep it out of the cached system message (put it at the tail of the turn prefix like memory/milestones) so it doesn't break prefix caching.

### 3.6 Better command output handling — P2

**[Idea]** For `run_command` (tests/builds), don't return raw head-truncated output. Keep first/last N lines **plus** lines matching error/fail patterns, and return a structured summary (`exit code, duration, N failures, first failure with file:line`). Consider a `run_tests` wrapper that knows common runners. This reduces the follow-up `read_file`s triggered by vague failures.

## 4. Editing across many files

### 4.1 Make edit failures actionable (stop telling the model to re-read) — P0

**[Verified]** On a failed `search`, the tool says "Re-read the file and try a smaller, unique snippet" ([fileTools.ts:164-167](src/tools/fileTools.ts)); on an ambiguous match it gives only a count ([:160, :170](src/tools/fileTools.ts)). Both push the model to re-read the whole file.

**Suggestion:**
- **Not found:** return the closest region (best whole-line fuzzy score, or longest common-prefix match) **with line numbers and the actual current text**, e.g. "Closest match at lines 88-93: …". The model can fix its snippet with zero extra reads.
- **Ambiguous:** list every match with line number and 1–2 lines of context, and suggest `occurrence: N` or a larger snippet.
- Add an optional `occurrence` (or `all: true`) parameter to `search/replace`.

### 4.2 Batch and atomic edits — P1

**[Verified]** One snippet per `write_file` call; each is a full model round-trip.

**Suggestion:**
- `edits: [{search, replace}, …]` per file in a single call (applied sequentially against the evolving text; all-or-nothing on failure with a per-edit report).
- A multi-file **`apply_patch`** (unified diff or structured list) staged as one atomic unit: either every file's edit is staged, or none is, with one coherent review card and one checkpoint entry. This is what makes multi-file refactors reliable.
- Optional **line-range edit** (`replace_lines {path, start, end, expected_hash, replace}`) as an alternative anchor for cases where search text is awkward (generated/repetitive code).

### 4.3 Stale-read guard — P1

**[Idea]** Record each file's content hash when the model reads it. At `write_file` time, if the file changed since (the user edited it, a hook reformatted it, another tab wrote it), return a warning with a diff of the changes rather than blindly applying a search/replace to something the model has not seen. This is the multi-tab / user-edits-while-agent-runs safety that the roadmap already lists as an open limitation.

### 4.4 Auto-verify after edits — P1

**[Idea]**
- After each accepted/applied edit, automatically collect **LSP diagnostics for the touched files** (diff against the pre-edit set, so pre-existing errors aren't blamed on the edit) and append new errors to the tool result. Already on the roadmap ("Auto-invoke `get_problems`"); it is also the strongest available replacement for the crude bracket-counter.
- Replace/augment `detectBalanceRegression()` ([fileTools.ts:315-329](src/tools/fileTools.ts)) — which is string/comment-unaware and documented as prone to false positives — with a real parse check where possible (LSP diagnostics, or tree-sitter via WASM if you want a zero-network dependency).
- Support **multiple verify commands** (typecheck + lint + tests) with per-command timeouts, not one (roadmap already notes this), and run the fast ones automatically after a batch of edits.

### 4.5 Line endings, BOM, encoding — P1 (test first)

**[Hypothesis, high-probability]** `write_file` splits and matches on `'\n'` everywhere ([fileTools.ts:36, :274-302](src/tools/fileTools.ts)). On a CRLF file:
- byte-exact `search` (with `\n`) won't match multi-line snippets;
- the fuzzy fallback *will* match (its `trim()` strips `\r`), but `applyFuzzyMatch()` then splices `replace` lines that have **no** `\r` into a CRLF file → mixed line endings in the diff.

Detect the file's EOL once, normalize for matching, and re-apply the file's EOL on write. Also preserve a leading BOM, and refuse or warn on non-UTF-8 files (indexing already skips them with a crude `�` check). Write tests for this before fixing (§8.3).

### 4.6 Cross-tab / sub-agent isolation — P2

Known limitation in the roadmap (shared `PendingEditManager`, no isolation). Once batch/multi-file edits exist, add a per-path **edit lock/lease** (or at least conflict detection at stage time) so concurrent tabs or sub-agents can't silently stage conflicting edits to the same file.

## 5. Retrieval and indexing for larger repos

**[Verified]** current behavior, from [workspaceIndex.ts](src/indexing/workspaceIndex.ts):

| Issue | Detail | Suggestion |
|---|---|---|
| Silent truncation | `MAX_FILES = 3000`, `MAX_CHUNKS = 4000`; anything past that is silently unindexed | Make configurable; **report coverage** ("indexed 3,000 of 11,240 files") in the UI and in `search_codebase` results; prioritize by import centrality/recency instead of `findFiles` order |
| Manual, full rebuild | Only the manual *Index Workspace* command; every build re-reads and re-hashes every file (roadmap: auto-index not built) | Auto-index on open; incremental re-index on save/create/delete via a file watcher; compare mtime+size before reading; only re-embed changed chunks (the hash-reuse already exists per chunk) |
| Legacy embedding API | `embed()` uses `/api/embeddings` with one string per request | Use the batch `/api/embed` endpoint (many chunks per call); raise concurrency; run at low priority so it doesn't compete with chat on the GPU |
| Storage | One JSON file with every vector as a JS `number[]`, rewritten in full on each save | Float32 binary file (or SQLite) with pre-normalized vectors and typed-array dot products; write incrementally |
| Ranking | Pure cosine + small open-tab/recency boosts; keyword search is only a *fallback* when embeddings are absent | **Hybrid**: BM25/keyword + embedding, fused (RRF); boost exact symbol-name matches; optional small reranker. Code queries are often lexical ("where is `retryPolicy` used") — embeddings alone are weaker there |
| Ignore rules | Hard-coded exclude list; the roadmap's `.forgeignore` isn't built | Honor `.gitignore` + `.forgeignore` in **both** the indexer and every file tool, from one shared implementation |
| Snippets | Truncated at 800 chars with no way to expand | Return `path:start-end` and let the model `read_file` that exact range (it already can) — but also include the enclosing symbol name |

## 6. Agent loop and orchestration

### 6.1 More than one tool call per model turn — P1

**[Verified]** The protocol is "exactly one action per turn" ([systemPrompt.ts:79](src/agent/systemPrompt.ts)), and the loop makes one tool call per model call. Exploring five files = five full model round-trips (each with its own prefill).

**Suggestion:**
- Allow a `calls: [...]` array (or several fenced blocks) per turn for **independent read-only tools** (`read_file`, `search_code`, `find_files`, `list_dir`, `get_problems`, git reads). Execute them concurrently, return results in one message. Keep write/exec tools strictly sequential.
- Add a first-class **`read_files`** tool as the simplest possible version for weaker models that won't emit an array.
- Keep the loop detector working on the *set* of calls.

### 6.2 Native tool calling with fallback — P1

**[Verified]** Forge uses a home-made text protocol (fenced `forge_action` block) and never sends Ollama's `tools` field ([client.ts](src/ollama/client.ts)). That was a deliberate model-agnostic choice; it also costs prompt tokens (the tool docs) and depends on the model obeying a format.

**[Idea]** Add an opt-in **native mode**: send `tools` (JSON-schema, derived from the same `TOOL_SPECS` + MCP schemas that already exist), parse `message.tool_calls`, and fall back to the text protocol when the selected model doesn't support tools. Native calls also naturally support multiple calls per turn. Per-model capability detection (try once, cache the result) avoids requiring the user to know. Always keep the existing tolerant parser as the fallback — don't remove it.

### 6.3 Read-only "explorer" sub-agents — P1

**[Verified]** Sub-agents are always launched with `mode: 'auto'` — full write/run access with no approvals ([agentLoop.ts:401](src/agent/agentLoop.ts)), and they get none of the parent's prompt cache.

**[Idea]** Add a `spawn_subagent {kind: "explore"}` that runs in a **read-only mode** (search/read/LSP tools only), on a cheaper/faster model if configured, and must return a **structured result**: `{findings, files: [{path, ranges, why}], open_questions}` with `file:line` citations. This is the right way to keep a big, read-heavy investigation out of the main context — the parent gets a few hundred tokens instead of 20 file reads. Also safer: an investigative sub-agent should not be able to edit your repo.

### 6.4 Redundant-work detection beyond identical calls — P1

**[Verified]** `LoopDetector` only trips on the **same tool + same args + similar result** ([loopDetector.ts:34-86](src/agent/loopDetector.ts)). Reading `a.ts` whole, then lines 1–200, then lines 1–150, then `a.ts` again never trips it.

**[Idea]** Add a *read-coverage* tracker (`path → covered line ranges + hash`): when a new read is ≥ ~80% covered by earlier reads of an unchanged file, answer from the ledger (§3.2) or nudge with an outline. Log it in the trace so the "redundant reads" metric (§1.2) is real.

### 6.5 Prompt guidance that pushes less reading — P0 (cheap)

**[Verified]** [systemPrompt.ts:82-83, :92](src/agent/systemPrompt.ts) currently contain a mix of "don't re-read" and "read a file before editing it". A local model follows the more concrete, more recent one. Rewrite the guidance around a workflow:

1. Locate: `search_code` / `find_symbol` / `find_files` (get line numbers).
2. Orient: `outline` or a **line range** around the hit — not the whole file.
3. Edit: `write_file` with a small unique snippet (the tool returns the location on mismatch).
4. Verify: diagnostics / tests.
And say explicitly: "Prefer a range or outline over reading a whole file; a file you already read is still in context unless the result says it was pruned."

Also worth an A/B on the eval suite: few-shot examples of this loop in the system prompt are typically worth more for a local model than more rules.

### 6.6 Budget awareness — P2

Track tokens and wall-time per turn (from the trace); surface "this turn used 180k prompt tokens across 22 steps" and let the user set a soft budget that pauses for confirmation. Pairs with the existing cost-aware planning.

## 7. Safety and robustness review (part of "thoroughly vetted")

Items found while reading the code. **Confirm each with a test before changing behavior.**

1. **Symlink escape** — [Verified]: `resolveWorkspacePath()` uses `path.normalize` + `path.relative` ([paths.ts:11-21](src/util/paths.ts)) but never resolves symlinks. A symlink *inside* the repo pointing outside it passes the check. Use `fs.realpath` on the target (or its nearest existing ancestor for new files) before the containment check, for reads, writes, deletes, and `cwd` on `run_command`.
2. **Hooks and workspace trust** — [Hypothesis]: `.forge/hooks/*` are executable scripts that run at `session-start`/`before-command`/etc. If a user opens a repo they cloned from someone else, its hooks would run. Gate hook execution (and repo-provided MCP servers/commands) on `vscode.workspace.isTrusted`, and require explicit opt-in per repo.
3. **`run_command` denylist** — [Verified it exists]; review how it's matched (string patterns are easy to bypass with `sh -c`, env indirection, or command substitution). Prefer allow-list-first for auto mode, and consider a sandbox (e.g. `sandbox-exec` on macOS) for Auto/Outcome modes, which run without approvals.
4. **MCP credentials in `settings.json`** — [Verified, documented limitation]: move `env`/`headers` secrets to `vscode.SecretStorage` (the roadmap notes this).
5. **Web tools** — keep the opt-in default; add a visible indicator when a turn used the network, and never let `web_fetch` content override instructions (treat fetched text as untrusted data — prompt-injection hygiene).
6. **Persistence edge cases** — chat store hardening exists (0.9.1); add crash-injection tests (kill during write) to keep it that way.

| Category | Example task | Pass check |
|---|---|---|
